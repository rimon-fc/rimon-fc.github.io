    What the pause actually is

    app.request_approval(prompt, operation_key=..., checkpoint=...) is a durable server-side pause, not an in-process wait:

    • the server records the approval, ends the attempt, sets the traverser to waiting and releases the lease, so the worker permit is free;
    • the decision arrives out of band (client.decide_approval, the Console, or any authorised caller) and may be approved or rejected;
    • the traverser is queued again with one extra attempt allowed — a continuation is not a retry against the capability's failure budget;
    • the handler then runs again from the beginning with a fresh lease, and request_approval returns the recorded decision instead of pausing.

    Because the handler replays, everything before the pause has to be idempotent. Here the case is written once with save_checkpoint(..., expected_revision=0); on the continuation load_checkpoint returns it, so the refunds.assess child is not submitted again. review.py prints the path so you can count the steps, and the result carries prepared_on_attempt: 1 next to attempts: 2.

    The prompt is built only from the checkpoint. That matters: an approval is keyed by (traverser, operation_key), and requesting the same key again with a different prompt is a 409 approval_conflict. Keep prompts free of clocks, random values and anything else that changes between attempts.

    Approvals are namespaced and owned: a non-admin caller lists and decides only its own traversers' approvals. Deciding the same approval the same way twice is accepted; deciding it differently afterwards is 409 approval_decided.

    Tests: tests/test_feature_examples_extended.py runs this node against a real daemon, including a decision taken while the server and worker are both down.
