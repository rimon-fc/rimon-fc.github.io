    README

    Rendered from examples/python/features/resilience/README.md; the source file is not modified.

    Three ways work goes wrong — a flaky dependency, one that never answers, and one nobody wants any more — against a provider fixture that runs locally. No keys, no network, no supplier.

    python -m examples.python.features.resilience.fixture_model --port 18899
export ATFGRAPH_MODEL_URL=http://127.0.0.1:18899 ATFGRAPH_MODEL_NAME=fixture-fast
target/debug/atfgraphd
python -m atfgraph.worker --module examples.python.features.resilience.agent:app
python -m examples.python.features.resilience.call

    fixture_model.py is an OpenAI-compatible /chat/completions endpoint that answers from the request: fixture-fast replies at once, fixture-flaky returns 503 for the first two calls carrying a given user message, fixture-slow stalls. When the request asks for a JSON schema the reply is built from that schema ("fixture <field>", 2, true, first enum value). It is a stub, not a model: it never invents a fare, a route or a policy.

    What each capability shows

    CapabilityDeclaredOutcome
    rebooking_notemax_attempts=3attempts 1 and 2 raise RetryableError, the server requeues, attempt 3 returns
    stalled_notetimeout_seconds=2the budget ends the call: failed/handler_timeout
    watchtimeout_seconds=600cancel() stops the poll between slices: cancelled

    Retries are the server's, not the handler's. Only a retryable error envelope (RetryableError, or HandlerError(..., retryable=True)) lets the server schedule another attempt, and only while the capability's max_attempts allows it. Any other exception is terminal on the first failure, which is what you want for input the provider will reject again. Each attempt gets a fresh lease and current_context().attempt — the driver prints the attempt.started and requeued events so you can see the sequence the server recorded.

    Budgets are enforced twice. The worker stops a handler that outruns timeout_seconds and completes the run with handler_timeout; independently the server gave the running attempt a deadline, so a worker that stops answering altogether has the same run marked timed_out instead. Either way the budget is what ends it, and call.py prints whichever arrived.

    Cancellation is cooperative but bounded. client.cancel() marks the run; the worker sees it on its next lease renewal, sets the context flag and cancels the handler task. A handler that awaits in small slices and checks app.cancel_requested() stops promptly and leaves its progress events behind; a handler that blocks without awaiting cannot be stopped until it yields. A cancelled task may not record more progress — that 409 cancelled from app.progress is the cancel arriving between slices.

    Tests: tests/test_feature_examples_extended.py runs all three paths against a real daemon with the fixture provider on an ephemeral port.
