    Co-consult on ATFGraph vNext

    Directory examples/python/co_consult

It registers 31 capabilities on one agent label (co-consult, version 0.3.0) and ships as an installable agent node (agentnode.yaml, entrypoint node:app).

    README

    Rendered from examples/python/co_consult/README.md; the source file is not modified.

    A complete travel consultation graph on the vNext Python SDK: intake, three parallel supplier desks (flights, hotels, activities), an advisory context desk, an evidence-checked proposal, and session chat with saved-shop follow-ups. It registers 31 capabilities on one agent label (co-consult, version 0.3.0) and ships as an installable agent node (agentnode.yaml, entrypoint node:app).

    Two explicit supplier modes, selected by CO_CONSULT_MODE:

    ModeFlightsHotels and advisory contextActivitiesNetwork
    fixture (explicit; tests and offline demos)synthetic offers labelled DEMO DATAsynthetic propertiessynthetic cataloguenone
    live (default)Sabre Flight Shop (POST {SABRE_API_BASE}/v1/offers/flightShop)SerpAPI google_hotels, google_flights, google, google_maps enginesLIVN Databricks vector search behind a managed MCP server (streamable HTTP, JSON-RPC 2.0)bounded async HTTP

    There is no silent fallback in either direction. A live supplier that is unconfigured, unreachable or rejects a request is reported as a failed desk with an actionable, credential-free error (not_configured: … set SABRE_API_BASE, http_401: SerpAPI google_hotels returned HTTP 401: Invalid API key…), the proposal is marked partial and the gap is listed. Fixture inventory is never substituted for a live result. Nothing books, holds or quotes: Sabre totals are supplier quotes to revalidate, hotel rates are indicative aggregator prices, and activity prices are catalogue from-prices, all kept in their own currency.

    Model-backed decisions are a separate switch and the default: CO_CONSULT_DECISIONS=model with the SDK's ATFGRAPH_MODEL_URL / ATFGRAPH_MODEL_NAME. Otherwise deterministic CO_CONSULT_DECISIONS=fixture uses deterministic fixture decisions and the proposal says so in confidence_caveats.

    flowchart TD
    entry[consult or chat] --> intake[intake_brief -> extract_brief]
    intake --> route[plan_trip -> resolve_route -> resolve_airport if needed]
    route --> flights[flights_desk]
    route --> hotels[hotels_desk]
    route --> activities[activities_desk]
    flights --> fare[flight_shop: fixture or Sabre -> rank_flight_offers -> interpret_fare_rules -> offer_detail from the saved shop]
    hotels --> property[hotel_search: fixture or SerpAPI -> rank_hotel_shortlist -> assess_property -> hotel_detail, cached per token]
    activities --> catalogue[frame_activity_query -> activity_search: fixture or LIVN MCP, up to twice -> rank_activities]
    fare --> context[context_desk -> plan_context_lookups -> context_lookup: fixture or SerpAPI -> summarise_lookup]
    property --> context
    catalogue --> context
    context --> propose[propose -> provenance_check + budget_fit -> compose_recommendation -> build_proposal]
    propose --> saved[Session memory: brief, shops, tracks, proposal]
    saved --> follow[chat follow-up or new selections; no supplier call]

    Every inter-traversal call is app.traverse through the graph server, so the path records each nested child with its own ID under one root_id. Raw supplier records stay in session memory under co-consult.shop.<shop_id>; only compact shortlists cross traversal edges.

    Common behaviour (suppliers/http.py, suppliers/config.py): one bounded HTTPPool (8 connections, 16 MB response cap), per-request timeout CO_CONSULT_SUPPLIER_TIMEOUT (default 60 s), CO_CONSULT_SUPPLIER_RETRIES (default 2) extra attempts with exponential back-off for transport failures and HTTP 408/429/5xx, no retry for other 4xx. Provider error messages are carried into the desk status after scrubbing configured secret values and Bearer …/api_key=… fragments; exception text is never returned. Configuration is validated by variable name; agent.check_live_configuration() refuses to start live mode when no supplier is configured and logs which names are missing otherwise.

    Tracing

    Every run of this node is traced to MLflow unless you switch it off: main.py sets ATFGRAPH_MLFLOW_TRACING=true, MLFLOW_TRACKING_URI=databricks and ATFGRAPH_MLFLOW_EXPERIMENT=/Shared/atfgraph/co-consult as defaults (anything already in the environment wins) and requirements.txt brings mlflow. The console's run page then shows the trace id and the experiment link; docs/mlflow.md describes what a trace contains. On a Databricks App the traces are written as the App's own service principal, so that principal needs permission to create or edit the experiment; on a laptop the databricks URI needs a profile (DATABRICKS_CONFIG_PROFILE=<name>) or DATABRICKS_HOST/DATABRICKS_TOKEN. Set ATFGRAPH_MLFLOW_TRACING=false to run untraced, or another MLFLOW_TRACKING_URI for a local store. By default a trace carries step names, timings, decision outcomes and token usage but no payloads; ATFGRAPH_MLFLOW_CAPTURE_PAYLOADS=true adds every step's inputs and outputs and every model call's prompt and reply, which is what MLflow evaluations and scorers read. Turn it on only where the experiment's readers may see the traveller's brief and the supplier results.

    Docker Compose

    Two routes exist; they do not mix.

    The working stack. deploy/docker/compose.yaml already runs the graph server and this node as its outbound worker (WORKER_MODULE defaults to examples.python.co_consult.main:app, fixture mode, label co-consult). It is the stack scripts/product/compose-smoke.sh and managed-compose-journey.sh verify, so use it whenever you want co-consult in containers:

    export ATFGRAPH_API_KEY="$(openssl rand -hex 24)"   # required: the server binds 0.0.0.0 in its container
target/debug/atfg deploy compose up --name demo --build
target/debug/atfg deploy compose status --name demo
target/debug/atfg --server http://127.0.0.1:18880 --api-key "$ATFGRAPH_API_KEY" ls
target/debug/atfg deploy compose down --name demo --volumes --forget

    Set CO_CONSULT_MODE=live and the supplier variables in the Compose environment (deploy/docker/.env) for live suppliers; deploy/docker/README.md covers the by-hand docker compose form, image tags and rollback.

    A standalone scaffold. To ship co-consult on its own against a server you already run, write a Dockerfile and compose.yaml into this directory:

    target/debug/atfg deploy scaffold examples/python/co_consult --target docker --label co-consult --module node:app
docker compose -f examples/python/co_consult/compose.yaml up --build

    The scaffold's worker runs python -m atfgraph.worker --module node:app --server "$ATFGRAPH_SERVER"; add the atfgraph package to requirements.txt first, as the scaffold notes, and point ATFGRAPH_SERVER / ATFGRAPH_API_KEY at your server. --target kubernetes writes a kustomize base under k8s/ instead. Neither scaffold output is committed here; the checked-in stack is the one under deploy/docker/.

    Sessions and follow-ups

    vNext sessions are server-created opaque IDs. consult and chat create one when session_id is absent and return it. Pass it back for follow-ups:

    {"session_id": "<returned>", "message": "Is that fare refundable?"}
{"session_id": "<returned>", "message": "Choose the five-star hotel", "selections": {"property_tokens": ["<property_token>"]}}
{"session_id": "<returned>", "message": "Search fresh options", "refresh": true, "hints": {"depart_date": "2027-05-08", "return_date": "2027-05-15"}}

    Conversation state lives in session memory (co-consult.state) with compare-and-set on its revision. Follow-ups and selection changes reuse the saved shops and make no supplier calls in either mode; the response carries the source shop_ids for every desk. Changing trip facts needs refresh=true; request_id deduplicates a retried turn; an unfinished attempt reports interrupted instead of shopping again. Session memory is owned by the principal that created the session (the worker's credential here), so the calling application must authenticate users and decide which sessions they may reuse.

    Verify

    cd python && .venv/bin/python -m pytest -c pyproject.toml ../tests/python_test_coconsult.py ../tests/test_coconsult_live.py -q

    python_test_coconsult.py runs the fixture graph through the in-memory contract double with a real worker (nested call counts, gates, provenance, currency safety, saved follow-ups, refresh, session isolation, duplicate and interrupted turns). test_coconsult_live.py starts local fake Sabre, SerpAPI and LIVN MCP services with realistic payloads, switches the process to live mode and checks the exact request shapes emitted, stored follow-ups without supplier traffic, child passenger types and currency separation, actionable partial failures, bounded retries and single re-authentication, not_configured without fixture fallback, source provenance, SSE-framed MCP replies, and the packaging entrypoint. These tests use local fixtures. Configure your own supplier credentials to run live searches.
