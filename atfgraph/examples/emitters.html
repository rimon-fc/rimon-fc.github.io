    Emitters demo

    Directory examples/emitters

    One Python node that exercises every built-in graph-server source: Stripe payments, GitHub pull requests and issues, a cron schedule, plus Slack, generic HMAC and generic Bearer inbound webhooks. Every handler is deterministic; the GitHub issues handler asks the configured model for a summary only when one is configured and otherwise records the issue with the reason the summary was skipped.

    Agent node label emitters-demo-agent, version 1.0.0.

    Capabilities

    CapabilityKindSignatureModuleSummary
    handle_inboundtraversal(trigger: TriggerContext | None = None) -> dictexamples/emitters/python/agent.pyCatch-all for UI-managed emitters: record the payload plus its provider context.
    handle_paymenttraversal(payment: dict, trigger: TriggerContext | None = None) -> dictexamples/emitters/python/agent.pyRecord a Stripe payment, deterministically.
    handle_prtraversal(event: dict, trigger: TriggerContext | None = None) -> dictexamples/emitters/python/agent.pyRecord a GitHub pull_request action.
    handle_ticktraversal(trigger: TriggerContext | None = None) -> dictexamples/emitters/python/agent.pyIncrement a cron-fire counter in global memory and record the wall-clock time.
    summarize_issuetraversal(event: dict, trigger: TriggerContext | None = None) -> dictexamples/emitters/python/agent.pySummarise a GitHub issue with the configured model on opened/edited/reopened.

    Non-default capability options: handle_inbound: accepts_manual_emitters=true; summarize_issue: timeout_seconds=120

    Quick start (local processes)

    From this repository's root with the SDK installed:

    # 1. Graph server with the demo signing secrets in ITS environment
STRIPE_DEMO_SECRET=demo-stripe-signing-secret-change-me \
GITHUB_DEMO_SECRET=demo-github-webhook-secret-change-me \
SLACK_DEMO_SIGNING_SECRET=demo-slack-signing-secret-change-me \
GENERIC_HMAC_DEMO_SECRET=demo-generic-hmac-secret-change-me \
GENERIC_BEARER_DEMO_TOKEN=demo-generic-bearer-token-change-me \
  target/debug/atfgraphd

# 2. The demo node as an outbound worker (it logs its webhook URLs after syncing)
python -m atfgraph.worker --module examples.emitters.python.agent:app

# 3. Fire signed Stripe, GitHub, Slack, HMAC and Bearer events (cron fires on its own)
python -m examples.emitters.python.fire_events
open http://127.0.0.1:18880/ui/

    fire_events.py waits for the server and for the worker's emitters, signs each fixture body exactly as the server verifies it, posts to /hooks/{emitter_id}, creates the three UI-managed emitters if they do not exist yet, and prints every admitted traverser's output. Re-running it produces fresh events because identifiers and delivery keys are randomized per run.

    Quick start (Docker Compose)

    cd examples/emitters
cp .env.example .env            # set ATFGRAPH_API_KEY (openssl rand -hex 24)
docker compose -p atfgraph-emitters-demo up --build --wait
cd ../..
ATFGRAPH_API_KEY=<the same key> python -m examples.emitters.python.fire_events
docker compose -p atfgraph-emitters-demo -f examples/emitters/compose.yaml down --volumes

    Both images are built from this checkout with the shared Dockerfiles in deploy/docker. The server binds a non-loopback listener inside its container, so it requires the API key; the worker and the driver send the same one.

    How the pieces fit together

    fire_events.py
   |   signs the body with STRIPE_DEMO_SECRET / GITHUB_DEMO_SECRET / ...
   v
POST /hooks/<emitter_id>            <- public ingest URL owned by the graph server
   |
   v
graph server:
   1. resolves the emitter, reads the secret named by secret_env from ITS environment
   2. verifies the source's signature over the raw bytes (401 otherwise)
   3. derives event type and delivery key (Stripe: body.type/body.id; GitHub: headers;
      Slack: event.type/event_id; generic: configured headers or a body digest)
   4. stores the inbound event, deduplicates on the delivery key, admits one traverser
   v
emitters-demo-agent worker (outbound; claims the task):
   - code-managed delivery: applies the binding's transform, binds and validates arguments
   - UI-managed delivery: raw body already validated on admission, arrives unchanged
   - injects TriggerContext (source, event_type, event_id, idempotency_key, managed_by)
   - handler runs deterministically and writes to global memory
   v
Console (/ui/): emitters, their events and the traversers they admitted

    The cron emitter needs no HTTP request: the server fires it once per due time and never twice for the same due time, even across a restart.

    Custom secrets

    Export your own values before starting the graph server and again before running the driver, so both sides use the same names:

    export STRIPE_DEMO_SECRET=... GITHUB_DEMO_SECRET=... SLACK_DEMO_SIGNING_SECRET=... \
       GENERIC_HMAC_DEMO_SECRET=... GENERIC_BEARER_DEMO_TOKEN=...

    The worker never reads these variables; secret_env is a name the server resolves. The demo defaults are placeholders, not provider credentials.

    Optional: the model-backed issue summary

    summarize_issue is the only handler that can make an external call. Configure an OpenAI-compatible provider for the worker (ATFGRAPH_MODEL_URL, ATFGRAPH_MODEL_NAME, ATFGRAPH_MODEL_API_KEY, optionally ISSUE_SUMMARY_MODEL) and the handler summarizes opened/edited/reopened issues. Without a provider it records the issue with summary: null and summary_skipped set; nothing is invented. For OpenRouter the base URL is https://openrouter.ai/api/v1; for a local fixture provider see examples/python/features/resilience/fixture_model.py.

    Pointing real Stripe / GitHub at the demo

    1. Expose the graph server publicly (for example ngrok http 18880).
    2. Read the Stripe emitter's URL from the worker log, GET /api/v2/emitters or the Console, and prepend the public host: https://<public-host>/hooks/<stripe_emitter_id>.
    3. Paste it into the Stripe dashboard's webhook settings with the value of STRIPE_DEMO_SECRET (or rotate to Stripe's signing secret and set that on the server) as the endpoint's signing secret.
    4. Repeat for GitHub: the handle_pr and summarize_issue emitters have separate URLs; set the secret to GITHUB_DEMO_SECRET and pick the pull_request and issues event types.

    Real provider events flow through the same pipeline as the driver's fixtures.

    Differences from the original

    • The node is an outbound worker; the original inbound agent port (8001), AGENT_CALLBACK_URL, heartbeat thread and startup banner are gone. Webhook URLs are /hooks/{emitter_id} and are printed by the worker and the driver.
    • @app.reasoner(...) became @app.traversal(...); accepts_webhook=True became accepts_manual_emitters=True; the catch-all takes the raw body as **payload because a UI-managed emitter delivers the validated object as is.
    • Memory writes use app.memory.global_scope() explicitly; the cron counter is a compare-and-set update, so concurrent ticks never lose a count.
    • summarize_issue no longer hard-codes an OpenRouter model id; the provider comes from ATFGRAPH_MODEL_* and the handler skips (with a reason) instead of failing when none is configured.
    • The generic HMAC and Bearer emitters declare an X-Delivery-Id idempotency header; without one the server derives the delivery key from the body, so identical bodies would deduplicate to one event.
    • fire-events.sh became fire_events.py on the SDK client; the demo secret defaults were renamed so they do not resemble real provider secret formats.
    • Compose builds the vNext graph-server and python-node images from deploy/docker; DID signing of trigger events is not part of vNext emitters.

    Tests: tests/test_migrated_ops_examples.py runs the worker and the driver against a real daemon with the demo secrets injected into the daemon only.
