    Retention operations

    Preview and apply pruning of old traversers, events and logs.

    retentionApply

    POST /api/v2/retention/apply

    Requires: admin role

    The same report as plan; with dry_run:false each eligible root is pruned in its own transaction under a root lock with eligibility re-checked, and a storage failure rolls that root back while the batch continues (action failed with error). Only the journal tables in pruned_tables are deleted; traverser rows, usage, run metadata, replays, emitter lineage, credentials, sessions and memory are retained, so idempotency keys stay spent and traversers.get keeps answering. Repeat with the same cutoff until scanned is 0, or page with next_after_seq. With mode sessions each eligible session's brief artifacts are deleted under the session row lock (rows_deleted.brief_artifacts); the session, its runs, memory and knowledge stay; page with cursor.

    retentionPlan

    POST /api/v2/retention/plan

    Requires: admin role

    Read-only report of the next batch (limit, default 100) of finished root executions in the caller's namespace whose whole tree finished strictly before cutoff, with the journal rows that would be pruned and the reason for every skip (active lease, unfinished descendant, recent activity, pending approval, active session). With mode sessions the batch is instead the sessions with brief artifacts whose last activity is strictly before cutoff (skips: session_active, unfinished_traverser, recent_activity), paged with cursor / next_cursor and reported under sessions. dry_run:false is rejected here; a body namespace field is rejected (400 invalid_retention_request). Non-admins get 403 before any read.
