    Access operations

    Access policies and connector grants: who may start which traversals, and which external connectors a namespace may reach. Server authorization is authoritative; these operations edit the rules it enforces.

    admitAccess

    POST /api/v2/access/admit

    Requires: invoke role, worker role

    Like evaluate but consumes at most one token per matching rate rule when allowed. This is for additional gateway operations: invocation admission is already charged centrally inside traversers.submit, so do not call it for submissions (they would be charged twice). retry_after_ms is set only for rate_limited.

    putConnector

    PUT /api/v2/access/connectors/{principal}

    Requires: admin role

    Bind an authenticated principal to an allow-list of operation patterns (exact names or `prefix*`, at most 128). Create with expected_revision absent or 0; replace with the current revision (409 revision_conflict otherwise). Grants restrict existing roles and never add any; Store::call rejects ungranted operations with 403 connector_forbidden while the connector's own read, evaluate and admit stay reachable.

    createAccessPolicy

    POST /api/v2/access/policies

    Requires: invoke role

    Create a durable admission policy for one exact node label the caller registered, or `*` for admins. principal and capability accept exact values or a single trailing `*`; embedded wildcards are rejected (400 invalid_access_policy). A matching deny, a violated constraint on a matching allow, or an exhausted rate bucket denies the invocation centrally inside traversers.submit with 403 policy_denied / constraint_denied or 429 rate_limited. No match preserves ordinary bearer authorization; allow rules never grant roles. Namespaces hold at most 1024 policies.
