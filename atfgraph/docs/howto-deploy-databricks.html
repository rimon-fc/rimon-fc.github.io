    Deploy to Databricks with `atfg databricks`

    atfg databricks deploys ATFGraph vNext to a Databricks workspace from one manifest: the graph server (daemon + Console) as an App on Lakebase, each agent node as its own App, and optionally the documentation site as a static App. The documentation is published on GitHub Pages (the SDK's site_url, for organisation members); the docs App is for workspaces that want the same site inside Databricks. It ships with the Python SDK's [databricks] extra as the console script atfg-databricks; atfg databricks … dispatches to it. Every command takes the workspace from a Databricks CLI profile you name — it is never chosen for you.

    pip install 'atfgraph[databricks]'          # the client installer's venv already has it
atfg databricks doctor --profile <p>        # tools, profile, Volume, release

    The two credentials never mix: the workspace OAuth token travels as Authorization (the Apps proxy), the ATFGraph key as X-API-Key. Secret values go through 0600 files into secret scopes and are never printed; evidence and state hold names, URLs and digests only.

    The everyday case: deploy the node you just built

    You built and smoke-tested a node locally with the atfgraph-vnext skill or by hand, you are logged in to a graph server that runs as a Databricks App (atfg login <url>), and you want it deployed:

    atfg databricks node deploy ./my-node --profile <p> --smoke <capability>

    One command does all of it:

    1. resolves the graph server and your key like atfg does (flag, environment, login file) and confirms it is ATFGraph vNext behind the workspace proxy; finds the server App from its URL;
    2. mints a dedicated token for the node (POST /api/v2/auth/tokens, roles invoke+worker — since 0.3.3 a worker registers its own labels without admin, under your own principal so sessions and approvals bind correctly); earlier tokens for the same node are revoked;
    3. creates the scope atfgraph-node-<label>, stores the token as api-key, and turns the node's .env into App configuration (*_KEY, *_TOKEN, *_SECRET, *PASSWORD* become secrets bound with value_from, everything else plain values);
    4. assembles the App bundle from the packaged template (worker entrypoint, your node as a package, the atfgraph wheel), runs the offline check, databricks bundle validate → deploy → run with the explicit profile; the bundle binds the server App with CAN_USE;
    5. waits for RUNNING, for the node's status page to say registered: true, and for the graph server to list the label; with --smoke it runs one traversal and prints its Console URL.

    Re-running after code changes redeploys the same App. --plan assembles and validates without touching the workspace. Exit codes: 0 deployed, 1 refused (configuration, auth, a crashed App), 2 connectivity. Other knobs: --env-file, --wheel, --reuse-caller-key, --wait, --bind-secret NAME=key (bind an existing key of the node's scope as an environment variable; no value travels through the tool).

    Two engines. With --profile the tool uses the Databricks CLI and databricks bundle (--engine bundle, the default on a laptop). Without a profile, or with --engine api, it uses the Databricks SDK and the Apps API: unified auth from the environment (DATABRICKS_HOST with the service principal's DATABRICKS_CLIENT_ID/CLIENT_SECRET, as inside a Databricks App), the bundle uploaded to /Workspace/Users/<caller>/atfgraph-nodes/<label>, the App created or updated with its resources (graph-server binding, secret bindings), a snapshot deployed. Registration (step 6) is the same for both. This is how the Studio node deploys the nodes it builds from its own App; a laptop with a profile may also pass --engine api.

    Afterwards: atfg databricks node status ./my-node, node logs, node list, and to take it down node remove (deletes the App and its scope and revokes the node's tokens; the server keeps the definition until it gains a delete route, so the Console shows the node as offline).

    Getting the graph server's key and logging in

    The server App reads its key from the secret scope named in the manifest (server.scope, default the App name) under api-key. server up writes it there when it is absent and never prints it. Anyone who can read that scope gets it back with the Databricks CLI; the value comes base64-encoded, so decode it and hand it straight to atfg login on stdin (nothing lands in shell history or a file you did not choose):

    databricks secrets get-secret atfgraph api-key --profile <p> -o json | python3 -c "import json,sys,base64;print(base64.b64decode(json.load(sys.stdin)['value']).decode())" \
  | atfg login https://<server app url> --api-key-stdin --edge-auth databricks --databricks-profile <p>
atfg whoami

    The Console at <server app url>/ui/ asks for the same value the first time; paste it there (the tab keeps it in sessionStorage and sends it as X-API-Key). A node deployed with node deploy never needs this key: it gets its own token, minted under your principal.

    The co_consult example runs live by default: it needs its supplier settings and a model provider (ATFGRAPH_MODEL_URL, ATFGRAPH_MODEL_NAME, and either ATFGRAPH_MODEL_API_KEY as a secret or no key, in which case the node signs model calls with its App's own service principal and node deploy grants that principal CAN_QUERY on the endpoint) in the --env-file you deploy with, and it refuses to start without them rather than serving demo data. For an offline demo set CO_CONSULT_MODE=fixture CO_CONSULT_DECISIONS=fixture explicitly; the fixture decision parser only understands key=value tokens, so free-text briefs stop at intake_brief/extract_brief in that mode. Structured output differs per endpoint: databricks-claude-sonnet-5 accepts response_format (and strict); the Claude Fable endpoints reject response_format and forced tool use, so only the schema-in-the-prompt shape works there. The SDK steps down through the shapes on its own (strict → plain → forced tool → prompt) from the release after 0.3.4; on 0.3.4 use Sonnet, or set ATFGRAPH_MODEL_STRUCTURED=prompt once your client has it. Sonnet also refuses the temperature parameter. A run whose usage rows say operation: fallback used the fixtures, whatever the App's environment says. The example also traces every run to MLflow by default (ATFGRAPH_MLFLOW_TRACING=true, MLFLOW_TRACKING_URI=databricks, experiment /Shared/atfgraph/co-consult, mlflow in its requirements): inside the App the traces are written as the App's service principal, which needs permission to create or edit that experiment; ATFGRAPH_MLFLOW_TRACING=false in the env file switches it off. Traces carry no payloads until ATFGRAPH_MLFLOW_CAPTURE_PAYLOADS=true is in the env file (then every step's inputs and outputs and every model call's prompt and reply are recorded, and MLflow evaluations can score them). Databricks serving states no price, so model calls show as unpriced until the env file carries an ATFGRAPH_MODEL_PRICES rate table; the Console then shows those costs as estimates.

    The operator case: a manifest per workspace

    atfg databricks init --profile <p> --catalog <catalog> --schema <schema> --release github:rimon-fc/atfgraph@vnext-<version>

    writes atfgraph.cloud.yaml:

    version: 1
targets:
  dev:
    profile: <p>                 # the only place a workspace is named
    catalog: <catalog>
    schema: <schema>
    volume: dist                 # /Volumes/<catalog>/<schema>/dist holds the releases and the state mirror;
                                 # leave catalog/schema/volume out for a target without a Volume (see below)
    require_confirmation: true   # prod targets cannot switch this off
server:
  app: atfgraph
  release: github:rimon-fc/atfgraph@vnext-<version>   # or @latest; or volume:/Volumes/<catalog>/<schema>/dist/vnext-<version>
  database: lakebase             # or {secret: <scope>/<key>} for an existing database URL
  lakebase: {project: atfgraph, branch: production, endpoint: primary, role: atfgraphd, pg_schema: atfgraph}
nodes:
  - path: ./my-node              # label, module and version come from its agentnode.yaml
    smoke: chat
docs:                            # optional: the documentation site inside the workspace
  app: atfgraph-docs
  site: ./site

    server.release is the release source. github:<owner>/<repo>@<tag> names a GitHub Release of the repository (@latest is GitHub's latest — never a draft or pre-release — and is resolved to its tag before the version is read); init --release accepts it as given, while a bare vnext-<version> still means that directory in the target's Volume, for a workspace that keeps the Volume channel.

    Then the reconciler verbs:

    CommandWhat it does
    atfg databricks plancompares the manifest with the workspace; lists the actions; exit 3 when there is work, 0 when there is none; mutates nothing
    atfg databricks applyperforms the plan in order: server, nodes, docs; stops at the first failure; a prod target asks for confirmation, and a plan that removes nodes names them and asks you to type remove (--yes when scripted)
    atfg databricks statusserver App state, URL, version and agent count; each node's App state, registration and source drift; the docs App
    atfg databricks doctorPython, PyYAML, the Databricks CLI, atfg, the profile, the Apps API, the Volume (when the target names one) and the release: a github: release must be reachable with the token and hold SHA256SUMS; a volume: directory likewise

    server up fetches atfgraph-server-app-<version>-linux-amd64.tar.gz from the release, verifies it against SHA256SUMS — for a github: release both are downloaded through the GitHub API on your machine, with GITHUB_TOKEN, GH_TOKEN, ATFGRAPH_CHANNEL_TOKEN or a logged-in gh's token, and pushed to the workspace as App source; the App never contacts GitHub — makes sure the Lakebase role and schema and the scope (database-url, api-key, credential-key) exist — creating them only when absent — creates the App with its three secret resources, patches the App's own URL into ATFGRAPH_PUBLIC_BASE_URL, imports the source and deploys, then checks /api/v2/server through the proxy. server upgrade --release … repeats that on a running App; server rollback redeploys the previous source folder; server status, server logs, server down [--delete]. Every verb that deletes something says what goes and asks for a typed confirmation before touching the workspace: node remove wants the label, server down --delete the server App name, apply with removals the word remove; --yes stands in for the prompt when scripted, and without a terminal the command refuses instead of guessing. docs publish [--site dir] publishes the generated site to the optional docs App (the published documentation itself is served from GitHub Pages); node rollback redeploys the previous kept bundle.

    State lives beside the manifest in .atfgraph-cloud/<target>.state.json and, once a workspace is involved, is mirrored to the target's Volume at deployments/<target>/<server app>/state.json: reads pull a newer mirror (another machine deployed last), saves push it back, so plan and status agree across laptops. The local file holds names, digests, URLs, workspace paths — no secrets); the last two node bundles and the fetched releases are kept under .atfgraph-cloud/builds and .atfgraph-cloud/releases.

    Scripted use: a runner upgrades the server

    server upgrade and server rollback run without a terminal when every input is on the command line: --profile (a ~/.databrickscfg profile — an OAuth service-principal profile with host, client_id and client_secret works; nothing in these verbs needs a user identity, and the source folder goes under the identity's own workspace home), --yes (stands in for the prod confirmation), --json (the result on stdout, progress on stderr) and --release github:<owner>/<repo>@<tag> (overrides server.release; GITHUB_TOKEN reads a private release). The result names the old and the new version, the deployment id, the rollback target and the URL:

    { "action": "server upgrade", "app": "atfgraph", "url": "https://…databricksapps.com", "console": "https://…databricksapps.com/ui/",
  "release": "github:<owner>/<repo>@vnext-0.3.6", "release_version": "0.3.6",
  "version": "0.3.6", "verified": "api", "console_status": 200, "app_state": "RUNNING",
  "deployment_id": "01f1…", "source_path": "/Workspace/Users/<identity>/atfgraph-vnext/atfgraph-0.3.6-<stamp>",
  "previous": {"version": "0.3.5", "deployment_id": "01f1…", "source_path": "/Workspace/Users/…/atfgraph-0.3.5-<stamp>"},
  "rollback": {"source_path": "/Workspace/Users/…/atfgraph-0.3.5-<stamp>", "deployment_id": "01f1…", "version": "0.3.5"} }

    Three things make this work from a service principal that only manages the App:

    • A target may name no Volume. Leave catalog, schema and volume out of the target (or set volume: null): the state stays in .atfgraph-cloud/<target>.state.json beside the manifest and is never mirrored — upload it as a run artifact when you want a record. doctor notes this instead of checking a Volume; volume: releases relative to the target are then unusable (github:, https://, volume:/Volumes/… and local directories are). A mirror that cannot be written never fails a verb: one WARNING line after the result.
    • An upgrade does not touch the secret scope. When the App's resources already bind database-url, api-key and credential-key, server upgrade skips the scope check (secrets_checked: false); creating or rotating secrets stays with server up.
    • The version check degrades, it does not abort. After the App reports RUNNING the tool reads /api/v2/server with the key from ATFGRAPH_API_KEY, else the scope's api-key when the identity may read it (verified: "api"); with neither it stops at /health and the Console's /ui/ status (verified: "health", version: null). Give the runner ATFGRAPH_API_KEY or READ on the scope when the version must be proven.

    server rollback with an empty state (a fresh checkout) takes the newest successful deployment in the App's own history whose source differs from the active one (adopted_from_history: true) and records the active one, so the rollback itself can be undone. plan resolves github:…@latest to the tag GitHub names before comparing versions; when it cannot (no token), it lists server.unresolved instead of failing. The repository's .github/workflows/deploy.yml is this flow on a GitHub runner, gated by the production Environment's protection rules.

    What it does not do

    It never chooses a profile, never prints a secret, never deletes a database or a secret scope it did not create for a node, and never reports success from a bundle deploy alone — registration on the graph server is the proof for a node, /api/v2/server for the server. node remove (and apply for a node the manifest no longer lists) deletes the App and its secret scope, revokes the node's tokens and unregisters the label on the graph server (DELETE /api/v2/agents/{label}, 0.3.3+); plan shows such removals as node.remove before anything happens. Live suppliers, model endpoints and load are yours to verify.

    What has been run against a real workspace so far (profile-scoped acceptance after each release, latest 0.3.4): status, plan, doctor, node deploy — from a manifest and manifest-less with --label, from the installed client, including a keyless node whose model calls were signed by the App's service principal — node remove (the typed/--yes confirmation and the server-side unregistration), apply adding and removing nodes, docs publish, server upgrade (the live graph server moved 0.3.1 → 0.3.2 → 0.3.3 → 0.3.4 with it) and server rollback. server up on a brand-new App and node rollback are implemented and covered by the offline tests but have not yet been exercised live; treat their first run on your workspace as the proof. The github: release source (server up|upgrade, doctor, init --release) is covered by the offline tests against a fake GitHub API; its first live use is the 0.3.6 release rehearsal.

    Run the verbs for one manifest one at a time: the state file beside the manifest is written last-writer-wins, so two concurrent runs against the same manifest can lose each other's updates.
