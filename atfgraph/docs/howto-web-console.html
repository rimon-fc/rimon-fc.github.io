    Use the web console

    Problem: you want to see what your agents are doing, test a capability, publish it, and find out where runs fail and what they cost, in a browser instead of the CLI.

    Open http://127.0.0.1:18880/ui/. The console is served by the graph server itself and talks to the same-origin /api/v2 API. From a source checkout, build it once with cd ui && npm ci && npm run build; the daemon serves the checkout's ui/dist, and reports "UI assets unavailable" at /ui/ until it exists. Installed distributions use share/atfgraph/ui beside the installation's bin directory. ATFGRAPH_UI_DIR overrides either location. Deep links such as /ui/runs/<id> and /ui/agents/<label> open directly, and the older /ui/traversers/<id> links still resolve.

    Every figure on every page comes from a recorded response. Where the API has no route for something (a denied-request history, for example) the page says so in place instead of showing a plausible number.

    Authentication

    When the server requires a bearer token, click the key icon in the top bar and paste it. It is kept in the tab's sessionStorage and sent in authorization headers, including streaming requests, never in URLs or localStorage. Closing the tab forgets it. Admin-only panels (connector grants, webhook, retention, observability settings) show the server's message and the role they need instead of disappearing.

    Pages

    The left rail has four groups.

    Operate

    • Overview: runs, failure rate, tokens and spend for the last 24 hours; a single failure-rate line per hour; the runs failing right now with their error codes; tokens by model and cost per run; agents and workers by state; all-time retained totals.
    • Runs: newest first, filtered by state, window, principal and session, with cursor pagination. Expanding a failed run shows the failing step first with the exact error envelope the worker returned, then the path. Open, Cancel and Restart use the server's traverser operations. The run detail keeps the Debug, Path, Events, Logs, Artifacts, Checkpoints, Usage, Metadata, Proofs and MLflow tabs, live over the run's event stream. The MLflow tab links to the trace the worker exported (trace id and experiment URL from run metadata); spans themselves are read in MLflow, not proxied by the server.
    • Costs: totals for 24 hours, 7 or 30 days, grouped by model, node, provider, day, run and principal, with input/output/cache token splits. Unpriced calls are counted as unpriced, never as zero dollars.
    • Observability: pick a run and read its trace waterfall (one bar per step), its event log, its run metadata and its node logs filtered by level, stream and text. While the run is active, new log lines are pushed over GET /api/v2/logs/events; finished runs are re-read on demand.

    Build

    • Agents: every registered node joined with its workers. Select one to Test a capability with a form generated from its input schema (or raw JSON) and watch the path, output, error envelope and usage arrive live; Publish it to the agent registry over MCP, A2A or HTTP; read its Schema (kind, tags and, for realtime entrypoints, provider and transport); and see its Versions with the runs each has served. Tags show in the node table; realtime entrypoints cannot be run from the Test tab because the server refuses to admit them.
    • Triggers: schedule, webhook and memory-change emitters with their next due time, enable/disable with revision checks, inbound event history with replay, fire-now with a delivery key, and creation of new triggers.
    • Studio: turn a brief into an agent node. My builds lists every build session (label, stage from the run's metadata, latest run, attachments, owner) with Open, Runs and Delete; New build creates the session, takes attachments (specs, documents, screenshots, samples, a reference node; each is stored on the server as a brief artifact and staged into the builder's workspace) and the typed brief form rendered from the node's own schema; a build shows Plan (the plan checkpoint and the plan gate with its questions), Build (harness progress per turn and the shell-command gate, with "approve every pending command"), Review (per-file diffs, the verification table and the accept gate), Install (the accepted tree, Deploy as a node App, the deploy plan gate, secrets the node needs, held on the server for the deploy run to collect once) and Continue chat for another turn on the same session. Delete discards the harness session through the node, then soft-deletes the session: attachments, session memory and knowledge go, the runs stay under Runs. Requires the studio node registered and a worker for it; without one the page lists builds but a new build stays queued.
    • Sessions & memory: your sessions from the server's session index (newest activity first, with label and run count), scoped memory entries with compare-and-set writes, the change feed and vector search.
    • Knowledge: BM25 corpus statistics per scope, documents, a search test with scored hits and citations, and document put/get/delete with revision checks.

    Evaluate

    • Playground: choose a node version and capability, fill the typed form or raw JSON, optionally bind a session, and run. Status, path, tokens, cost and output update live; every run here is a real traverser. Runs started in the tab are listed for re-running and comparison.
    • Compare: two runs side by side: status, duration, steps, tokens, cost, first failing step, an aligned path diff and a line diff of the outputs.
    • Evaluations: case sets of inputs with assertions for one capability. Run a set against a version; every case becomes a real traverser and is scored on status, output, duration, tokens and cost. Scores are grouped by version so a regression is visible as a moved pass rate.

    Govern

    • Policies: access policies (allow, deny, rate limit) with create, enable/disable and delete; an access evaluator that explains the decision reason; pending approvals with approve/reject. Input and output guardrails run in the node's worker (guardrails=[...] in the Python SDK) and surface as guardrail_violation errors on the Runs page. Budgets cap tokens, cost or runs per principal, node, target or namespace over a rolling window and show what each window has consumed. A denied-request history is labelled as not available.
    • Access: what each role may do, stored API tokens (create with roles and expiry, rotate, revoke; the secret is shown once), the principals seen, connector grants, signing identities, credentials, the tag policy and ledger, and DIDs. Tokens in atfgraph.yaml under auth.tokens stay valid and are not listed.
    • Health: server identity and features, workers, model-health probes, node log ingestion settings, the observability webhook with delivery status, stored runtime documents (save, apply, delete) and retention preview before apply.

    The top bar has search (/ or ⌘K) across pages, runs and nodes, the token entry and a light/dark theme toggle that persists; without a stored choice the console follows the operating system.

    Managed server on Databricks Apps: where the credential comes from

    Behind the Apps proxy the Console first needs the workspace login (single sign-on) and then the graph server's own key, which it asks for once and keeps in the tab's sessionStorage as X-API-Key. The key sits in the server App's secret scope (atfgraph, key api-key, unless the deployment chose other names). Read it back with the profile that deployed the server; the CLI returns it base64-encoded:

    databricks secrets get-secret atfgraph api-key --profile <p> -o json | python3 -c "import json,sys,base64;print(base64.b64decode(json.load(sys.stdin)['value']).decode())"

    Paste the printed value into the Console prompt, or feed it to atfg login <url> --api-key-stdin --edge-auth databricks --databricks-profile <p> for the CLI. Never put a Databricks token in that box: the proxy already carries it in Authorization.
