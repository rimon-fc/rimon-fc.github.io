    Install ATFGraph vNext

    install.sh lives at the root of the repository and ships inside every release set. It finds a Python 3.10 or newer, trying python3.12 and its neighbours before python3 (set ATFG_PYTHON to choose one; macOS's system 3.9 is refused with one sentence), and runs scripts/product/bootstrap.py, which verifies checksums, extracts safely, installs into a prefix you own and checks the result. No compiler, no sudo, no shell-profile edits.

    There are two kinds of artifact, and they install different things:

    ArtifactContainsInstall withFor
    Client bundle atfgraph-client-<v>-<os>-<arch>.tar.gzthe atfg CLI, the atfgraph wheel, the three coding-assistant skillsinstall.sh --from …people who use a managed graph server; nothing runs locally but the CLI and your nodes
    Self-host bundle atfgraph-vnext-<v>-<os>-<arch>.tar.gzatfgraphd, atfg, the console, the wheel, docs, examples, skills, the migration toolinstall.sh --bundle DIR / --archive TAR.GZ / --sourcerunning a graph server on this machine from a packaged artifact

    The client bundle has no daemon and no console. A release set (what package-artifacts.sh --release-set assembles and what a GitHub Release of the repository holds) contains client bundles for linux-amd64 and darwin-arm64, the Linux daemon and its App bundle, the wheel and sdist, the contract, the skills bundle, install.sh with bootstrap.py, release-manifest.json and SHA256SUMS; it does not contain self-host bundles. A workspace that keeps the Unity Catalog Volume channel holds the same set under /Volumes/<catalog>/<schema>/<volume>/vnext-<version>/.

    Client: the guided install

    One line installs the client and finishes the setup. The installer shipped with a release knows its own repository, so the piped form needs no --from from 0.3.10 on (in 0.3.9 that default was inert: pass --from github:rimon-fc/atfgraph@latest there). The gh form is the canonical one because the repository is private:

    gh release download --repo rimon-fc/atfgraph --pattern install.sh --output - | bash -s --

    On a terminal it detects the platform, Python, the GitHub login, the Databricks profiles in ~/.databrickscfg and the coding assistants on the machine, prints a summary, and asks at most three questions: what you will do (build agent nodes, operate a workspace, or just call agents), which Databricks profile is ATFGraph's when more than one exists, and whether to add <prefix>/bin to PATH in your shell file. Then it verifies and installs as before, and finishes the job:

    • Login. With a profile chosen, it finds the graph server App in the workspace (the App named atfgraph, or --server URL), reads the server's key from the secret scope atfgraph (--secret-scope to change) through that profile, and hands it to atfg login … --api-key-stdin. The key is decoded in memory and never printed; atfg login verifies it against the server. --no-login skips this.
    • PATH. With consent (or --path), one marked block # >>> atfgraph >>> … # <<< atfgraph <<< is appended to the file your $SHELL implies (~/.zshrc, ~/.bash_profile or ~/.bashrc, ~/.config/fish/config.fish); a second install finds it and changes nothing; atfg uninstall removes it. --no-path never edits a shell file. When the shell is unknown, the line is printed for you.
    • Skills. Installed into every coding assistant detected (Claude Code, Codex) when the release ships them; --skills none opts out, --skills claude limits.
    • Config. ~/.config/atfgraph/config (mode 0600, no secrets) records the profile, server, role, version and channel you chose; atfg databricks reads profile from it, so --profile becomes an override rather than a requirement. Nothing is written when nothing was decided.
    • Proof. atfg doctor, then atfg ls against the server, then three lines: what is installed, where you are connected and as whom, and one command to try for your role.

    Without a terminal (a pipe, CI, --yes) nothing is asked: the role is client, the shell file is not edited unless --path is given, and login happens only when the profile is unambiguous (--databricks-profile, or --yes with exactly one profile on the machine). --json prints the outcome as one document. Unknown flags are reported in one sentence and ignored, so an older installer never dumps its usage at a newer command line. A failed login or skill install never fails the installation; the ending says what to do instead.

    Client: install.sh --from

    Releases are GitHub Releases of the repository — rimon-fc/atfgraph, tag vnext-<version> (releases up to 0.3.7 stay on rimon-fc/atfgraph-server). The repository is private; collaborators with read access use gh, so the installer presents a GitHub token to the release API: GITHUB_TOKEN, GH_TOKEN or ATFGRAPH_CHANNEL_TOKEN from the environment, otherwise the token of a logged-in gh (gh auth login once). The token needs read access to the repository.

    # install.sh and bootstrap.py are assets of every release: download the two, point them at the release
gh release download vnext-<version> --repo rimon-fc/atfgraph \
  --pattern install.sh --pattern bootstrap.py --dir ./atfgraph-install
sh ./atfgraph-install/install.sh --from github:rimon-fc/atfgraph@vnext-<version> --skills claude
# @latest is GitHub's latest release — never a draft or a pre-release
sh ./atfgraph-install/install.sh --from github:rimon-fc/atfgraph@latest

    A github: source takes no --profile. The installer reads the release's SHA256SUMS first, downloads the one client bundle for this platform from its API asset URL, refuses it on any checksum mismatch or a missing entry, extracts it safely, validates the bundle's own install-manifest.txt, then creates <prefix>/venv with the wheel and runs atfg doctor (--no-sdk skips the virtualenv). The token goes to api.github.com only; it is dropped on the redirect to the object store that serves the asset. The github: source is exercised by the installer's offline tests against a fake GitHub API; its first live use is the 0.3.6 release rehearsal.

    The same verification applies to the other sources:

    # a release directory (downloaded assets, or a checkout of one), or an https URL serving the release files
sh install.sh --from <release directory or URL> --prefix ~/.local/atfgraph-vnext
# a Unity Catalog Volume, where a workspace still publishes releases; the Databricks profile is always explicit
sh install.sh --from /Volumes/<catalog>/<schema>/<volume>/vnext-<version> --profile <profile>
databricks fs cat dbfs:/Volumes/<catalog>/<schema>/<volume>/vnext-<version>/install.sh --profile <p> \
  | sh -s -- --from /Volumes/<catalog>/<schema>/<volume>/vnext-<version> --profile <p>

    A plain http:// source is accepted only from localhost. Afterwards:

    export PATH="$HOME/.local/atfgraph-vnext/bin:$PATH"
atfg login https://<your graph server>       # saves the key (0600); add --edge-auth databricks --databricks-profile <p> behind the Apps proxy
atfg ls

    Self-host bundle

    ./install.sh                       # newest self-host artifact for this platform in target/dist/release
./install.sh --source              # build the artifact first (needs Rust and the SDK wheel), then install it
./install.sh --bundle DIR          # an extracted atfgraph-vnext-<version> directory
./install.sh --archive TAR.GZ      # a packaged tarball; its sidecar SHA256SUMS is verified

    These run from the server checkout. The Windows equivalent ships inside the artifact as install-windows.ps1.

    Options

    OptionDefaultMeaning
    --prefix DIR~/.local/atfgraph-vnextWhere everything lands. Relative paths are resolved against the current directory. Spaces are fine.
    --skills claude,codexnoneAlso install the bundled coding skills into those harnesses, using the installer shipped in the artifact.
    --no-startstartSelf-host bundle only: install without starting the server. Client installs never start a server.
    --listen HOST:PORT127.0.0.1:18880Address for the started server. 0.0.0.0 is reported as 127.0.0.1 in the URLs.
    --python EXEthe interpreter running the installerInterpreter for the skill installer, for <prefix>/venv (client installs) and for the pip install hint.
    --from WHERE—Client install from github:<owner>/<repo>@<tag> (or @latest), a release directory, an https URL or /Volumes/... (see above).
    --profile NAME—Databricks CLI profile for a /Volumes/... source; required there, refused for every other source.
    --no-sdk—Client install: skip creating <prefix>/venv with the wheel.

    Environment: ATFG_BOOTSTRAP_RELEASE_DIR replaces target/dist/release as the place auto-detection looks; ATFG_PYTHON sets the default --python; GITHUB_TOKEN, GH_TOKEN or ATFGRAPH_CHANNEL_TOKEN (in that order) is the token for a github: source, else the token of a logged-in gh.

    What gets installed

    Client bundle (--from):

    <prefix>/
  bin/atfg                         the CLI
  venv/                            a private virtualenv with the atfgraph wheel installed (unless --no-sdk)
  share/atfgraph/
    atfgraph-<version>-py3-none-any.whl   the wheel; `atfg install` finds it here on its own
    resources/skills/              the four coding-assistant skills (build, use, personal, topology)
    resources/scripts/install-skills.py
    resources/databricks/          the node-App deployment kit: bundle/ (databricks.yml, worker_entrypoint.py,
                                   requirements.in), deploy-databricks-node.py, check_databricks_bundle.py.
                                   `python3 <prefix>/share/atfgraph/resources/databricks/deploy-databricks-node.py <node_dir> --profile <p>`
                                   deploys a node you built to a Databricks workspace without an SDK checkout: the
                                   script finds the bundle template and the offline check beside itself (from an SDK
                                   checkout it uses deploy/databricks/bundle and scripts/product/); --template-dir and
                                   --wheel override the lookup
    install-manifest.txt           every installed path with its SHA-256
    version.json                   kind: client, version, contract stamp, target, source identity

    Self-host bundle (--bundle, --archive, --source), in addition:

      bin/atfgraphd                    the graph server daemon
  bin/atfg-docs                    opens the bundled copy of the documentation site (published on GitHub Pages)
  share/atfgraph/
    config/atfgraph.yaml           a sample server configuration
    docs/                          public guides
    resources/                     examples, skills, site, scripts/install-skills.py
    uninstall-local.sh             removes exactly the paths in the manifest
  data/graph.db                    created by the started server (never listed in the manifest)

    The installer prints this map with the real paths when it finishes, and for a self-host bundle the started server's URL, UI and API addresses and the stop command. To use atfg without a path for the current shell:

    export PATH="$HOME/.local/atfgraph-vnext/bin:$PATH"

    An atfg from another product already on PATH is left alone and mentioned in the output. Nothing is ever written to /usr/local/bin.

    Nothing is written until the artifact is proven

    The installer refuses, with exit code 2 and an empty prefix, when any of these fail. The message says which check failed and what to do instead.

    1. Tarball against its sidecar. --archive needs a SHA256SUMS from the same build next to the tarball, with an entry for that file name. A missing sidecar, a missing entry or a digest that does not match is a refusal. If you only have the extracted directory, use --bundle.
    2. Archive members. Absolute paths, .. components, symlinks, hard links, devices and FIFOs are refused before extraction starts. The archive must hold exactly one top-level atfgraph-vnext-<version> directory. Modes are normalised to 0755 for executables and 0644 otherwise.
    3. Bundle structure. install-local.sh, bin/atfg, bin/atfgraphd, share/atfgraph/install-manifest.txt and version.json must exist and none may be a symlink.
    4. Manifest digests, both ways. Every path the manifest lists must exist and hash to the recorded SHA-256, and every file under bin/ and share/ must be listed. A file the manifest does not know about is as much a refusal as a corrupt one. Only the manifest may mark itself - instead of a digest.

    Only after all four pass is the artifact's own install-local.sh handed the copy into the prefix.

    When something fails after validation

    Exit code 1 means the artifact was sound but an install step failed. The prefix may be partially or fully written; the message says which step and what to do.

    FailureWhat the message saysState of the prefix
    install-local.sh exits non-zero, or exits 0 without producing bin/atfg and bin/atfgraphdthe exit code and the script's own outputwhatever the script managed to write
    the installed atfg --version does not run on this machinethe exit code; the binary was built for another platform or is blockedfiles are in place
    the server does not startre-run with --listen 127.0.0.1:<free port>; the install itself is completecomplete
    a skill install failsthe exact command to re-run by handcomplete; other harnesses named earlier were installed

    The prefix may already contain an install: re-running over it replaces the manifest's files and leaves everything else, including data/graph.db and files you added yourself, untouched. A prefix path that is an existing file fails the copy step and the file survives.

    Uninstall

    ~/.local/atfgraph-vnext/share/atfgraph/uninstall-local.sh --prefix ~/.local/atfgraph-vnext

    It removes exactly the paths listed in install-manifest.txt and refuses, with nothing deleted, if any listed path is a symlink, is not a regular file, reaches outside the prefix, or has changed since install (--force overrides the last one). --dry-run prints the plan. Directories are removed only when empty, so data/, installed agent node packages and anything you put there survive. Graph data under ATFGRAPH_VNEXT_HOME or ~/.atfgraph-vnext is never touched; add --remove-prefix to remove the prefix directory itself once it is empty.

    After installing

    A client install talks to a graph server somewhere else:

    PREFIX=~/.local/atfgraph-vnext
$PREFIX/bin/atfg login https://<your graph server>
$PREFIX/bin/atfg whoami
$PREFIX/bin/atfg ls
$PREFIX/bin/atfg install /path/to/your-node --python $PREFIX/venv/bin/python   # the wheel beside atfg is used
$PREFIX/bin/atfg run your-node

    A self-host install has the server too:

    $PREFIX/bin/atfg server status
$PREFIX/bin/atfg docs                                    # bundled documentation on loopback
$PREFIX/bin/atfg install $PREFIX/share/atfgraph/resources/examples/python/co_consult --python python3
$PREFIX/bin/atfg run co-consult

    atfg install uses the wheel beside the binary, so no package index is needed for the SDK (there is no PyPI package). The runner in share/atfgraph/resources/examples/run.py does the same and refuses any atfg that is not this product.

    Building the artifact yourself

    ./install.sh --source (server checkout) runs scripts/product/package-artifacts.sh --sdk-wheel <wheel built from this repository's python/>, which builds the release binaries and the web UI, takes the wheel as an explicit input, writes version.json, the install manifest and the tarball with SHA256SUMS into target/dist/release, and proves the result installs and runs from a fresh directory before the installer proceeds. package-artifacts.sh --debug reuses the debug binaries for a quick local artifact.

    Verification

    scripts/tests/test_bootstrap.py and test_bootstrap_fetch.py run the installer against synthetic artifacts in temporary directories: valid bundles and archives, sidecar and manifest corruption, path traversal, symlink, hard-link and special-file members, two top-level entries, paths with spaces, partial failures of the copy, binary, server and skill steps, reinstalling over a prefix with foreign files, and every usage error. It never touches a real home directory or prefix. The github: source runs against a fake GitHub API: a tag and latest resolved to the concrete release, a draft or pre-release latest refused, the client bundle fetched from its asset URL and verified, the token order, --profile refused, and the messages for a missing or refused token. Nothing there reaches the network.
