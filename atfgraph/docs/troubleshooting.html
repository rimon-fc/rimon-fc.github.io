    Troubleshooting

    Messages exactly as the CLI, the server and the Python worker print them, so a search for the text lands here. Each entry says what the message means and what to do. Request ids and pids vary; everything else is verbatim.

    A memory write failed with value_too_large

    value is 5242881 bytes, over the 4194304 byte limit; split the payload, summarise it, or store it as an artifact

    Memory is where a node is meant to put something too big to return, so its limit is four times the output limit — but it is a limit. Unbounded it made the output cap decorative: park the payload under a key, return the key, and it is in the database anyway, in a table with no size column, read by the change feed and by every scope that can see it.

    Nothing is partially written; the key keeps its previous revision. A payload over this bound is a modelling decision rather than a transport one — split it, keep a summary and page the detail, or attach it to the step as an artifact.

    To hand a large payload between steps of one run, use a reference rather than inventing a key:

    handle = await app.references.put("offers", offers)   # ref.offers.<digest>
...
offers = await app.references.require(handle)

    The handle is the memory key, it is stable across a retried or resumed attempt so a replay does not duplicate the payload, and it is scoped to the run so two runs producing identical payloads do not collide. See decisions for the replay behaviour this protects.

    A traverser failed with output_too_large

    output is 1310720 bytes, over the 1048576 byte limit; store the payload as an artifact (POST /api/v2/traversers/{id}/artifacts) and return its id instead

    The node returned more than the server will store for one traverser. This is a failure, not a truncation: nothing oversized is kept, status is failed and retryable is false, because returning too much is a property of the handler rather than a transient fault.

    Every other payload in the system is capped too — input reads at 64 KiB, artifacts at 512 KiB, memory changes at 64 KiB, vector metadata at 16 KiB — and the output cap is the most generous at 1 MiB precisely because a result is legitimately larger than the brief that produced it.

    The fix is to stop returning the payload and return a handle to it. Store the large part as an artifact and put its id in the output. There is no Agent-level helper for this yet, so go through the client, which sends the current lease as execution authority on its own:

    from atfgraph import current_context

ctx = current_context()
artifact = await app.client.put_artifact(
    ctx.traverser_id, "offers.json", json.dumps(large_payload).encode(), "application/json"
)
return {"status": "ok", "artifact_id": artifact["id"]}

    put_artifact takes bytes, not a string, and the server owns the 512 KiB cap — it answers 413 rather than the SDK duplicating the limit. A payload too big for one artifact has to be split or summarised; that is a modelling decision, not a transport one.

    To find out which capability is close to the line before it crosses it, every single-traverser read now carries output_bytes, and GET /api/v2/usage/totals?group_by=capability attributes cost to the same capability names — see decisions.

    The CLI cannot reach the server

    atfg: cannot reach graph server at http://127.0.0.1:18999: error sending request for url (http://127.0.0.1:18999/api/v2/agents)

    Nothing is listening at that address. Run atfg server status; if it reports no record, atfg server start. If you meant a different server, set ATFGRAPH_SERVER or pass --server. Exit code 1.

    Nothing is registered

    no elements registered
    no traversers

    Not errors. The server is up but no worker has registered a node, or nothing has been started yet. Start a worker with atfg dev or atfg run. If a worker is running and its label still does not appear, it is pointed at a different server URL or namespace; check its log for registration or authentication errors.

    The target is wrong

    atfg: target must be `label.capability`, got `badtarget`

    A target always has two parts joined by one dot. atfg ls prints them in the ELEMENT column.

    atfg: agent_not_found (404): agent nope is not registered [request 327e6229-a7eb-48d0-ac6a-6c66a726256c]

    No node with that label is registered on this server. Exit code 1.

    The input is wrong

    atfg: --in must be a JSON object (the traversal's named inputs)

    You passed a JSON array or scalar. The input is an object whose keys are the capability's named inputs, unwrapped: --in '{"name":"Ada"}'.

    atfg: --in must be a JSON document: expected ident at line 1 column 2

    The text after --in is not JSON at all. Quote it for your shell.

    atfg: invalid_input (422): input does not match schema: "name" is a required property [request 26ac5366-9a56-48fb-97ae-c84177b9174e]

    Valid JSON, but it does not match the capability's input schema. The message names the field. Exit code 1.

    The traverser does not exist

    atfg: traverser_not_found (404): unknown traverser [request c9ec0e4b-08a4-44d6-aff0-4f46eb76889f]

    Printed by show, wait, path and cancel. Check the id, and that you are talking to the server that created it. Exit code 1.

    The traverser finished but did not succeed

    traverser 99e794ae-ec1e-4e06-a38c-daf063fb79ab failed (hello.greet)
error: {
  "code": "ValueError",
  "message": "name must not be empty",
  "retryable": false
}

    The handler raised. code is the exception class, message its text. Exit code 3, which traverse and wait also use for cancelled and timed_out. Read the path with atfg path <id> to see which step failed.

    Waiting timed out

    traverse without --async, and wait, exit with code 2 when the traverser is still not terminal after --wait-timeout seconds (default 300). The traverser keeps going; atfg wait <id> again, or atfg cancel <id>. A traverser that stays queued has no worker for its label: check GET /api/v2/workers or atfg list.

    The Python interpreter cannot import atfgraph

    atfg: /usr/bin/python3 cannot import the atfgraph package:
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'atfgraph'
install it with `/usr/bin/python3 -m pip install ./python` or point --python at an interpreter that has it

    atfg dev checks before it starts the worker. Pass --python .venv/bin/python (or whichever interpreter you installed the package into), or install it as the message says.

    atfgraph (python)  missing  python3 cannot import atfgraph; pip install ./python or use `atfg install`

    The same condition as reported by atfg doctor.

    The Python interpreter is too old

    atfg: checking Python version (requires >=3.10) failed (exit status: 1):
ATFGraph requires Python 3.10 or newer; use --python python3.12 or your virtual environment interpreter

    atfg install refuses an interpreter below 3.10. The system python3 on macOS is 3.9. Pass --python python3.12 or a virtual environment interpreter.

    The package is not installed

    atfg: not-installed is not installed (no /Users/you/.atfgraph-vnext/packages/not-installed/installed.json); `atfg install <source>` first

    Printed by run, stop, logs and uninstall for a name that atfg install has not created. atfg list shows what is installed.

    The configuration file is invalid

    error: atfgraph.storage.url: `mysql://x` must start with sqlite: or postgres://
error: atfgraph.server.listen: 0.0.0.0:18880 is not loopback and no auth tokens are configured; the daemon refuses to start this way (set auth.tokens or ATFGRAPH_API_KEY)
invalid: 2 error(s), 0 warning(s)

    From atfg config validate. Each error: line names the YAML path. The second one is the development-mode rule: a server that listens off loopback must have at least one token or ATFGRAPH_API_KEY. Exit code 1; with --strict, warnings also fail.

    Scaffold refuses to overwrite

    atfg: my-node/.dockerignore exists; pass --force to overwrite

    atfg deploy scaffold never overwrites an existing file without --force.

    HTTP error envelopes

    Every non-success response from /api/v2 has this shape:

    {"error":{"code":"not_found","message":"No such API operation"},"request_id":"1c40f9bb-f720-4bb2-8e46-a58af50d595b"}
    codeStatusMeaning
    not_found / No such API operation404The path is not an operation on this server. Often an older daemon than the binary you built: atfg server status shows the running version; restart it.
    agent_not_found404No node with that label is registered.
    traverser_not_found404Unknown traverser id.
    invalid_json / Request body must be valid JSON400The body did not parse.
    invalid_input400 or 422The body or a query value is well-formed but wrong: cursor is malformed, since must be a non-negative integer, input does not match schema: ….
    invalid_query / roots_only must be true or false400A query flag has a value outside its enum.
    unauthorized401No key, or a key this server does not know. Send the ATFGraph key as X-API-Key: <key> (behind a platform proxy, Authorization carries the proxy's token, never the key).
    payload_too_large413The body exceeds the server's limit.
    storage_unavailable503The database is not reachable. Check the daemon log named by atfg server status.

    The daemon serves an old API

    If GET /api/v2/workers, /api/v2/stats, /api/v2/model-health or /api/v2/runtime/settings return No such API operation while the contract lists them, the running atfgraphd predates the binary you built. atfg server status prints the pid record with its start time; atfg server stop then atfg server start picks up the new binary.

    The worker registered but tasks never run

    The worker log (atfg logs <name> or the atfg dev terminal) should show a steady POST …/api/v2/worker/claim "HTTP/1.1 200 OK" line every couple of seconds. That is the worker asking for work. If those lines are present and traversers still sit queued, the worker is enrolled on a different server than the one you are submitting to; compare the --server values on both sides. If the lines show a status other than 200, the worker's credentials are being refused; the status and the daemon log say why.
