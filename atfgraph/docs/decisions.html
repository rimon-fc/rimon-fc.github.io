Type to search.

    Decisions: confidence you can query, and a human when it matters

    Problem: a traversal asked a model for a judgement, the model was not sure, your code quietly used a coded default instead, and the step still says succeeded. Nothing in the path, the logs or the totals distinguishes that run from a healthy one. You find out when someone compares two runs by hand.

    That is not hypothetical. It is how the feature described here came to exist. A travel-planning node ran 34 steps where the same request had previously run 40; six of the difference was one decision returning confident: false, which threw away a four-lookup research plan and substituted a single generic question. The output read "1 of 1 advisory lookups answered."

    Everything below was captured from a running server. Off loopback add the ATFGraph key as X-API-Key: <key> (Authorization is reserved for a platform proxy's credential).

    What a decision is

    A decision is a traversal whose job is one typed judgement: it calls a model, returns a schema, and reports its own confidence. It is dispatched exactly like a traversal — nothing branches on the kind — so declaring one changes what the graph and the console know about the step, not how it runs.

    @router.decision()
async def plan_context_lookups(situation: str, model: str | None = None) -> dict:
    ...

    CapabilityKind is now traversal, skill or decision, and the kind travels onto every recorded step:

    [{"kind": "decision", "status": "succeeded", "target": "docs.plan"}]

    Step 1: say what confident means

    A self-reported confidence flag is the model grading its own homework. If the field carries no criterion, it is being asked to assess itself against a standard nobody wrote down — and that arbitrary boolean is then wired to a hard fallback.

    Give every such field a criterion specific to its decision, and state the cost where the cost is high:

    class ContextPlan(BaseModel):
    lookups: list[PlannedLookup] = Field(description="Only the lookups this brief needs. At most four.")
    confident: bool = Field(description=(
        "False ONLY if you cannot name a single worthwhile lookup. False DISCARDS every lookup "
        "you listed and replaces the whole plan with one generic fare question, so a plan you are "
        "merely unsure about should still be confident. Uncertainty belongs in the questions, not here."
    ))

    Step 2: close the enums

    A field that lists its valid values in prose accepts anything. Downstream code then filters out what it does not recognise, so an invented value and a genuinely unconfident model produce the same silent outcome.

    ContextEngine = Literal["fare_insights", "destination_context", "map_context", "web_context", "reviews_context"]

class PlannedLookup(BaseModel):
    engine: ContextEngine = Field(description="Which advisory engine answers this question.")

    A Literal becomes an enum in the JSON schema, which constrains generation rather than filtering after it, and anything else fails validation loudly.

    Step 3: record the outcome

    Pass confidence_field and the SDK records the decision's own confidence on the usage row that produced it:

    return await app.ai(schema=schema, system=system, user=user, confidence_field="confident")

    The field is named by the caller, not assumed: confident is your node's vocabulary, not the SDK's. This works because app.ai records usage before it returns, so the parsed result is already available — which matters, because the usage insert deduplicates on (traverser, attempt, call_id) and a second write to attach the outcome would be dropped rather than merged.

    A recorded row:

    {"capability": "plan", "confident": false, "fallback": "model reported confident=false after proposing 3 lookup(s)",
 "input_tokens": 1412, "output_tokens": 96, "model": "verify-model", "operation": "chat", "source": "llm"}

    Both fields are nullable and absent is not false. A call that reported neither stays distinguishable from one that reported an unconfident decision, for the same reason cost_usd is null rather than zero when no price is known.

    Record on the model call, not on the handler. A resumed attempt re-runs the handler from the top. If you record usage unconditionally rather than where the model is actually consulted, a replay writes a second row for a call that never happened and every total downstream overcounts. Using app.ai gets this right for free, because app.ai is what a cache or checkpoint skips.

    Step 4: aggregate it

    group_by=capability buckets usage by the traversal or skill that spent it, which is what turns "which decisions are we falling back on" into one request:

    GET /api/v2/usage/totals?group_by=capability
    {"groups": [{"key": "plan", "calls": 2, "unconfident_calls": 2, "fallback_calls": 1,
             "input_tokens": 2824, "output_tokens": 192, "total_tokens": 3016,
             "priced_calls": 0, "unpriced_calls": 2, "cost_usd": null, "cost_complete": false}],
 "group_by": "capability", "scanned": 2}

    unconfident_calls and fallback_calls are counted apart on purpose. A decision can be unconfident without falling back, and can fall back with no model reply at all — so one number could not mean both. Every group_by value carries them, including none, model, run and day.

    Step 5: measure it, where the provider lets you

    A self-report is an opinion. A token probability is an observation. Ask for the distribution and the SDK records one beside the other, never instead:

    export ATFGRAPH_MODEL_LOGPROBS=1

    Opt-in, because some gateways reject the parameter rather than ignoring it, and one diagnostic is not worth turning every call into an error. atfgraph.model.boolean_field_probability finds the token that actually produced a boolean field and returns its probability, landing in the row's extra as confident_p. It returns nothing when the answer cannot be established beyond doubt — no logprobs, field absent, token not recognisably a boolean. A weak signal is better than a fabricated one.

    Read the caveat before you trust the number: this is the model's probability for the value it emitted, which is not a calibrated probability of being correct. A high probability on a false is a model that is confidently unsure.

    Step 6: calibrate before you threshold

    scripts/calibrate-decisions.py --server http://127.0.0.1:18880

    Reads the ledger and reports, per capability, confidence rate, fallback rate and mean measured probability. Read-only; it adds no storage.

    The label: retrieval feedback

    Reliability means "when a decision said it was confident, was it right", and right needs a labelled outcome. Retrieval used to have none — a search reports scanned and strategy and stores nothing — so the script had to say out loud that it could not compute one.

    Record a verdict where a retrieved item is consumed:

    await app.memory.feedback(item_key, "useful")       # or irrelevant | outdated | wrong

    Four verdicts, a closed set, because a free-text label cannot be aggregated and an open one stops being comparable between runs. Append-only: an item useful in March and outdated in June is two true facts, so calling it twice records two rows rather than overwriting. Inside a traversal the capability is taken from the lease and any value in the body is ignored, so feedback joins to usage rows on something neither side can invent.

    POST /api/v2/retrieval/feedback/totals   {"group_by": "capability"}
    {"groups": [{"key": "plan", "useful": 2, "irrelevant": 0, "outdated": 1, "wrong": 1, "total": 4}],
 "group_by": "capability", "scanned": 4}

    Every verdict appears with its count, zero included: a bucket missing wrong and a bucket with zero wrong are different facts. With feedback recorded, the calibration table gains judged and useful columns and reports labelled: true.

    It labels the inputs, not the judgement. A useful-rate says whether the items a decision was handed helped; whether the decision itself was right still needs evals. Those are different questions, and do not set a gating threshold on a confidence rate alone — that is the difference between a measurement and a guess wearing its clothes.

    Calibration needs volume, and volume normally means spend. It does not have to: decision routing and supplier routing are separate switches, so real model calls with fixture suppliers give you cheap repetitions. In the bundled travel example that is CO_CONSULT_DECISIONS=model CO_CONSULT_MODE=fixture. Expect most decisions to report confident=false in that combination: the synthetic offers and context do not answer the questions the model is asked, so low confidence is the calibration working, not a model or deployment fault. A failed decision records fallback: "model call failed: <error>: <message>" in the run's usage rows (0.3.4+ keeps the message; earlier releases kept only the error type).

    Step 7: gate it on a human

    When discarding the decision is expensive, stop and ask instead:

    verdict = await app.request_approval(
    {"question": "run this plan anyway?", "proposed": lookups},
    operation_key="plan_context_lookups",
    checkpoint={"plan": result.model_dump()},
)
if verdict["status"] == "approved":
    return {"lookups": lookups, "confident": True}

    request_approval is a durable server-side pause, not an in-process wait. The worker drops its lease and goes away; the traverser waits on the server through restarts and deploys; GET /api/v2/approvals is the queue and POST /api/v2/approvals/{id}/decide takes approved or rejected. When it is decided the handler starts again with a fresh lease and the same call returns the decision.

    Two things are load-bearing, and both follow from that replay:

    • Attach the proposal and reuse it. The handler re-runs from the top, so a second consultation would produce a different plan and the human would have approved one that never ran. Read the checkpoint first and only consult the model on a miss; see approvals, pauses and checkpoints for the mechanics and expected_revision compare-and-set.
    • Use a stable `operation_key`. It is the idempotency handle: the same key returns the existing decision instead of asking again.

    Gate on the event — a decision is about to be discarded — rather than on a confidence threshold, until step 6 has given you a number that means something. And gate narrowly: an approval queue nobody drains is worse than a logged fallback. In the travel example the gate is off unless a capability is named in CO_CONSULT_GATE_DECISIONS.

    The order is the point

    Each step is cheap only because the one before it happened:

    1. Record the outcome. Nothing else works without the data.
    2. Aggregate it, and the standing question becomes a query.
    3. Measure it, so you have something better than a self-report to calibrate.
    4. Calibrate against observed outcomes.
    5. Gate on a human, on the few decisions where it pays.

    Doing 5 first gives you a threshold you cannot defend. Doing 1 and skipping 2 records evidence nobody reads — which was the original failure: the confidence was already in the recorded path, and no query returned it.

    A note on vector storage

    Memory vectors are stored as little-endian float32, base64-encoded, not as JSON text. The search is still an exact linear scan of the scope — there is no approximate index — so this changed the constant, not the complexity.

    Measured on a real daemon at dimension 1024 (databricks-gte-large-en), before and after:

    vectorssearch beforesearch afterdatabase beforeafter
    10041 ms8 ms1.8 MB1.2 MB
    500196 ms36 ms10.2 MB3.4 MB
    2,000776 ms136 ms39.6 MB12.6 MB
    5,0001,955 ms337 ms98.3 MB30.7 MB

    87% of the old per-vector cost was turning 21,153 characters of [0.0142,-0.981,...] back into numbers; the arithmetic was the other 13%.

    Two consequences worth knowing. Values round to float32 on write, so a caller storing float64 of its own reads back about seven significant digits — embedding models emit float32, so this is normally exact for real embeddings. MemoryVectorWrite.embedding says so in the contract.

    And the scan is still linear: scanned in every response is the whole scope. Sub-second now means roughly 15,000 vectors rather than 2,500, but it is a small-corpus store, not a search engine. Past that you want a real index — pgvector in Postgres keeps the data where it is, which is a different and larger decision than this one.

    Verify it yourself

    scripts/verify-decisions.py

    Starts an isolated server on its own port with its own temporary database, exercises all five steps, prints a pass/fail table, and leaves the server up so you can browse it. No model or supplier calls, so no credentials and no spend.

    Where to see it in the console

    PageWhat to look at
    A, BCostsThe By decision panel: one row per capability, with Unsure and Fell back beside the token columns. A capability that reported neither shows a dash, not a 0
    CRuns → a run → PathThe Kind column reads decision. The step list indents children by depth and each step is selectable
    EPoliciesThe Approvals panel lists a paused decision with its operation_key, and approves or rejects it
    Dcommand linescripts/calibrate-decisions.py; an analysis over recorded runs, not a live view
    Fcommand linePOST /api/v2/retrieval/feedback/totals; recorded from the SDK with app.memory.feedback

    Two things are deliberately not there. A decision step has no distinct colour or icon in the path diagram — it is named in the Kind column and nowhere else, because status is what a reader scans a path for. And per-step confidence is not shown on the step itself: the outcome is recorded on the usage row that produced it, so it aggregates per capability rather than decorating one step.

    Monitor over HTTP covers the same data as requests, and observability covers the ledger it lives in.
