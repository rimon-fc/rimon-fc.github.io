    Why ATFGraph, and how it compares

    An agent framework helps you write what an agent does. ATFGraph is what runs agents once they have to work together, run unattended, and answer for what they did. It is a graph server: agent nodes register their capabilities with it, every call between capabilities crosses it, and every crossing is recorded as a step on a path. The result of a run comes back with the complete record of how it was produced: which node did what, in what order, with which model, at what cost, with what confidence, and from which evidence.

    The server never calls a model. Your Python does, through whatever provider or endpoint you choose. That separation is the design: intelligence lives in nodes you own; routing, scheduling, durability, policy and the record live in one server you operate.

    What production means for an agent

    Prototypes are judged on whether they answer well. Production agents are judged on six other things. ATFGraph is built so each of them is a property of the runtime, not a habit of the team.

    Callable. A capability is a typed, versioned function on a node. Anything with the URL and a key can start it over one HTTP contract (API reference), from the CLI (atfg traverse label.capability --in '{…}'), from the generated Python, TypeScript or Go clients, or from another node with await app.traverse("label.capability", …). Other agents can discover it through the Agent Registry and Discovery surface and consume it over HTTP, MCP or A2A (Discovery publication).

    Durable. A run is a traverser the server schedules. It holds a lease; if the worker dies the lease expires and the step is requeued. RetryableError and max_attempts give the server, not the handler, control of retries. A handler can stop for a human with await app.request_approval(...) and the traverser waits without holding a worker; when someone decides, the handler re-runs from the top and its checkpoints make that replay safe, across a server restart (Approvals, pauses and checkpoints).

    Bounded. Every capability has timeout_seconds. A worker has a capacity of permits; a parent waiting on its children releases its permit, so a node with capacity one can run a tree of a hundred steps without deadlock (Calling other nodes). Model tool loops are capped by rounds and calls; a coding harness is capped by wall clock and, when the provider streams cost, by dollars (Delegating to a coding harness).

    Observable and priced. Every step records input, output, timing, attempt and parent. Every model call records tokens, model, and cost when the provider states one; when it does not, a price table you configure prices it and the row says cost_source: table. Unknown cost stays null, never zero. Traces go to MLflow or OpenTelemetry; the Console shows runs, costs by model and node, a trace waterfall, and a Debug view per run (Observability, Use the web console).

    Governed. The server authenticates every call with API tokens that carry roles, applies access policies (allow, deny, rate limit) and connector grants before a step runs, and enforces budgets. Nodes never talk to each other and open no inbound port; they trust the server, not one another (Identity, credentials and access boundaries).

    Provable. A path can be signed by the node's server-held key and verified offline. A node can enrol a DID and issue execution credentials that bind hashes of a run's input, output and error to that identity. Evidence keeps its origin: knowledge citations are stable doc_id#ordinal references, stored payloads are addressed by a digest that includes the run that produced them, and the travel example refuses to compose a proposal whose quoted prices no longer match the supplier records it saved (Knowledge, examples/python/co_consult).

    Two decorators and a handful of app. calls carry all of this. There is no workflow DSL: the graph is traced from what the code actually did, not declared in advance. A fan-out is asyncio.gather over app.traverse calls; a dependency is an await; a branch is an if. The path shows the shape that ran (A DAG across nodes).

    Decisions with confidence you can query

    This is the feature that most separates a demo from a system, and it came from a production incident recorded in Decisions. A travel-planning node ran 34 steps where the same request had run 40 before. Six of the difference was one model call answering confident: false; the code threw away a four-lookup research plan and substituted a single generic question, and every step still said succeeded.

    ATFGraph's answer has three parts. A capability can be declared a decision, so its kind travels onto the step. The schema's confidence field carries a written criterion, so the model is not grading itself against a standard nobody wrote. And app.ai(..., confidence_field="confident") records the decision's own confidence, and the fallback the code took, on the usage row of the call that produced it. Absent is not false: a call that reported nothing stays distinguishable from one that reported doubt. The Console aggregates these, so "how often does this decision fall back" is a query, and the chapter shows how to calibrate before you threshold and how to gate on a human when it matters.

    Provenance: the answer can only rest on what actually happened

    Models paraphrase, remember and invent. A production agent that quotes a price or cites a passage must be able to show where it came from. ATFGraph gives that at three levels. The path records which step, model call and tool call produced each output. Evidence keeps its origin: a knowledge answer carries doc_id#ordinal; a stored payload's handle mixes the run into its digest, so identical bytes from two runs are two pieces of evidence, not one; the travel example saves every raw supplier response and checks each selected offer and every quoted field against it before a proposal is built, and answers follow-up questions only from those saved records. And identity: signed paths and execution credentials let an auditor verify, offline, that this node produced this output from this input.

    The same discipline applies to money. The SDK never estimates. Cost is recorded from a stated price or from a table you configured and labelled; a call the provider did not price is unpriced and says so.

    Where it runs

    The graph server is a single Rust binary with its own database. Nodes are Python workers that connect outbound. The documented targets are Databricks Apps (server and nodes, with atfg databricks verbs and a workspace-secret login), Docker Compose and Kubernetes; a node can also run as a long-running worker, as one bounded invocation per event on a serverless host, or as a realtime session (Deploy to Databricks, Deploy with Docker Compose, Deploy to Kubernetes, Hosting). Model calls go to whatever you configure; on Databricks that is the workspace's model-serving endpoints, priced by a table when the endpoint reports no cost, with traces in MLflow (MLflow tracing). Releases are built on GitHub, verified by digest, and installed by one line from the release assets with a guided client installer that logs you in from a secret scope and installs the builder skills into Claude Code and Codex (Install).

    How it compares

    Authoring frameworks: LangGraph, CrewAI, PydanticAI, OpenAI Agents SDK, LlamaIndex, Google ADK

    These are where most teams start and they are good at it: prompts, tools, structured output, hand-offs, in-process graphs, and in some cases a hosted tracing product. Their graph, when they have one, lives inside one process and one runtime; their memory is an object the framework owns; their retries and timeouts are what the process does before it returns. When the agent must be called by other software, run longer than a request, call agents owned by another team, or account for cost and provenance, teams put a service, a queue, a database and a dashboard around the framework.

    ATFGraph is that surround, designed as one thing. The graph is between processes; each edge is a routed, leased, recorded step; state is server-held with scopes; identity and policy are the server's. You can keep using a framework inside a traversal: the server does not care what produced the answer. You gain more by using app.ai, app.traverse, app.memory and app.harness directly, because they record usage, tool calls and child steps on the path without adapters, and because a decision's confidence only lands in the ledger through app.ai.

    Platform agent services: Amazon Bedrock agents, Databricks Agent Bricks, and their peers

    Cloud platforms offer managed agent runtimes: Amazon Bedrock's agents and its AgentCore runtime, gateway, memory and identity services; Databricks Agent Bricks with the Mosaic AI agent framework, MLflow tracing and evaluation; Azure AI Foundry's agent service; Google Vertex AI's agent engine. As of this writing they remove operations and integrate deeply with their own platform's models, data and identity.

    The trade is ownership and shape. They run agents as the platform's objects, on the platform's terms, and cross-agent work is usually a supervisor pattern within one account. ATFGraph is Apache-2.0 licensed, self-hosted, and runs on those platforms rather than inside them: on Databricks it deploys as Apps, calls the workspace's serving endpoints, reads keys from secret scopes and writes traces to MLflow, while keeping its own model of nodes, paths, decisions, provenance and identity that would move unchanged to Compose or Kubernetes. Agent Bricks is declarative and model-centred: you describe a knowledge assistant, an extraction task or a supervisor over existing endpoints and Databricks builds and tunes it. ATFGraph is code-first and system-centred: you write nodes, and the server records and governs how they call each other. Teams on Databricks can use both: Agent Bricks agents and serving endpoints are things a skill can call, and the call becomes a step on the path.

    Workflow runtimes: Temporal, Restate, Inngest, Prefect, Dagster

    They give durable execution, retries and history for arbitrary code, and they do it well. They do not know what an agent is: no capability kinds, no model usage or cost per step, no confidence, no memory scopes, no discovery, no agent identity, no provenance of evidence. ATFGraph has the durable core they have (leases, attempts, checkpoints, pauses that survive restarts) built around the agent-specific record. If your organisation already runs one of them, a traversal can be started from a workflow step and the path is the agent-level record inside it.

    Coding harnesses used directly: Claude Code, Codex, Gemini CLI, OpenCode

    Alone, a harness is a very capable process in a directory with the operator's credentials and no upper bound. Inside ATFGraph it is one step of a traversal: confined to a working directory, tools off unless listed, a wall-clock deadline, a dollar cap that kills the run when the provider's streamed cost crosses it, every CLI event on the path as progress, and a typed answer validated against a schema. A supervised pattern is documented: a read-only pass plans, a durable approval pauses, an approved pass applies. The same CLIs are also the builders: the installer puts the ATFGraph skills into Claude Code and Codex, and atfgraph-vnext builds a node from a brief (Describe what you want to build).

    Visual automation builders: n8n, Zapier, Make

    Good at connectors and personal or team automations. ATFGraph is for agents as code: tests against an in-process daemon, versions, evaluation sets, generated clients, and a production record. A builder's flow can call a capability over HTTP when the two meet.

    Other agent backends

    Several projects, many of them open source, now run agents as callable, durable, governed services with identity and audit; that is ATFGraph's own category. Where they differ is in their choices. ATFGraph's are: a single inbound endpoint with outbound-only workers, so no node opens a port; the path as the primary object, with steps that carry kind, confidence and cost; provenance checks on evidence, not only audit of actions; Databricks Apps and MLflow as first-class targets; Python as the one authoring runtime, with generated clients for the rest. Evaluate on those.

    Building it yourself

    Some teams can. The list they own is the one this page describes: routing, scheduling, leases, retries, checkpoints, memory scopes, discovery, policy, identity, cost accounting, tracing, deployment and support, before the first agent does anything useful. ATFGraph exists so that time goes into the agents.

    When ATFGraph is the right choice

    • Other systems, or other teams' agents, need to call this agent, and you need to say who may.
    • The work takes minutes or hours, must survive a restart, and sometimes needs a person in the middle.
    • Agents call agents, and you want one record of the whole tree rather than logs from each.
    • Finance wants cost by model and node; security wants who did what; compliance wants proof that quoted facts came from real records.
    • You run on Databricks and want agents that use its endpoints, secrets and MLflow without becoming platform objects.
    • You want Claude Code or Codex doing part of the work, bounded and recorded.

    When it is not

    • A single-process prototype, a notebook experiment, or an assistant one person supervises: a framework is enough.
    • Retrieval over documents is the whole problem: a RAG library or a platform knowledge assistant is simpler.
    • You want no operations at all and are content with one platform's agent objects: use that platform's service.
    • Your agents must be authored in TypeScript or Go: ATFGraph generates clients in those languages, but nodes are Python.

    Questions people ask

    Does the server call models? No. Nodes do, with any provider or endpoint. The server records the steps and usage.

    Can I keep my LangGraph or PydanticAI code? Yes, inside a traversal. Use app.ai for the model calls you want in the ledger with confidence and cost.

    Can I use Claude Code, Codex, Gemini CLI or OpenCode? Two ways. As builders, through the bundled skills the installer adds to Claude Code and Codex. As workers, through app.harness(prompt, provider="claude-code") and its siblings, with tools off by default, a deadline and a dollar cap (Delegating to a coding harness).

    How does it fit Databricks? Server and nodes deploy as Apps; model calls go to serving endpoints and are priced by a table when the endpoint reports no cost; keys come from secret scopes; traces go to MLflow. Nothing about the graph model is Databricks-specific.

    Do I need Rust? Only to build the server from source. Releases ship the server binary, the CLI and the Python wheel; a client install needs Python 3.10 or newer and gh.

    Licence? Apache 2.0.
