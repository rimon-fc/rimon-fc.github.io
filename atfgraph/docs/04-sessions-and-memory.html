    Sessions and memory

    By the end of this page you will be able to attach traversers to a server-created session, read and write memory in the four scopes with compare-and-set revisions and TTLs, store and search vectors, and react to memory changes from a worker. It requires only the SDK and a running graph server; the sessions and memory_lab examples run with no provider configured, and the vector snippets use hand-written embeddings.

    Sessions are created by the server

    A session is one conversation across many traversers. The server creates it (POST /api/v2/sessions); the SDK exposes that as await client.create_session(), which returns the id. Attach traversers to it with session_id= on submit or traverse, or with atfg traverse --new-session / --session ID from the CLI. Adapted from examples/python/sessions/call.py:

    from __future__ import annotations

import asyncio
import os

from atfgraph import Client


async def main() -> None:
    async with Client(os.getenv("ATFGRAPH_SERVER")) as client:
        session = await client.create_session()
        for text in ("pack passports", "book airport transfer", "check visa rules"):
            result = await client.traverse("notebook.note", {"text": text}, session_id=session, timeout=60)
            print(result)
        stored = await client.memory_read("session", "notes", session_id=session)
        print("memory revision", stored.revision, "notes", stored.value)
        print(await client.traverse("notebook.forget", {}, session_id=session, timeout=60))


if __name__ == "__main__":
    asyncio.run(main())

    Inside a handler the session is current_context().session_id; children submitted with app.traverse inherit it. The server serializes root turns per session, so two concurrent notes to one session never race, while their children still run concurrently (tests/python_test_worker.py::test_root_session_turns_are_serialized_children_bypass).

    Client.create_session() takes no arguments. The server also accepts a caller-chosen id in the request body and returns the existing session for a repeated id (tests/test_integration.py::test_named_protocol_session_is_reused_without_losing_memory); examples/python/memory_lab/call.py reaches that with client.transport.request("POST", "/api/v2/sessions", json_body={"id": name}) because the typed method does not expose it.

    Two helpers cover a root that starts without a session. await app.bind_session(session_id) binds the running root traverser to a session before it submits any children; with session_scope(session_id): directs default memory and child submissions at a session for the duration of the block. examples/python/co_consult/main.py uses both in _ensure_session and chat.

    The four scopes

    app.memory (python/atfgraph/memory.py) hands out MemoryScope objects. The server derives the namespace from authentication and the actor from the principal.

    ScopeFactoryIdentified byNotes
    sessionapp.memory.session(session_id=None)session_idWithout an argument it uses the running traverser's session; outside a session-bound traverser it raises NoExecutionContext.
    actorapp.memory.actor()the caller's principalactor_id is a hint only; naming someone else's actor is refused with AuthError.
    workflowapp.memory.workflow(root_id=None)root_idDefaults to the running traverser's root; the root must exist and be owned by the caller, else AuthError.
    globalapp.memory.global_scope()nothingShared by the namespace. global_() is a retained spelling.

    app.memory.default() picks a scope for you: session when the running traverser has one, otherwise workflow inside a handler, otherwise global. The convenience methods app.memory.get/set/update/delete(..., scope="session") route through default() unless you name a scope.

    The handler from examples/python/sessions/agent.py touches all four:

    from __future__ import annotations

from atfgraph import Agent, current_context

app = Agent(node_id="notebook", version="1.0.0")


@app.traversal()
async def note(text: str) -> dict:
    """Append ``text`` to this session's notes; return everything remembered so far."""
    ctx = current_context()
    if not ctx.session_id:
        raise ValueError("submit this traversal with a session_id")
    session = app.memory.session()
    notes = await session.update("notes", lambda current: (current or []) + [text])
    turns = await app.memory.actor().update("turns", lambda c: (c or 0) + 1)
    total = await app.memory.global_scope().update("all_notes", lambda c: (c or 0) + 1)
    await app.memory.workflow().set("last_note", text)
    return {"session_id": ctx.session_id, "notes": notes, "actor_turns": turns, "global_notes": total}


@app.traversal()
async def forget() -> dict:
    deleted = await app.memory.session().delete("notes")
    return {"deleted": deleted}

    tests/python_test_examples.py submits three notes to one session and one to another and asserts the sessions do not mix, that the stored notes value is at revision 3, and that a submission without a session fails with the session_id message.

    Read, write, delete with revisions

    Every write returns a revision; every read returns a MemoryValue with value, revision and found (revision 0 when not found).

    CallReturnsBehaviour
    await scope.read(key)MemoryValueRaw read.
    await scope.get(key, default=None)valuedefault when not found.
    await scope.exists(key)bool
    await scope.set(key, value, expected_revision=None, ttl_seconds=None)new revisiondata= is a retained keyword for the value.
    await scope.delete(key, expected_revision=None)boolFalse when nothing was there.
    await scope.update(key, updater, default=None, attempts=8)new valueRead, apply updater (sync or async), compare-and-set; retries on conflict.

    Compare-and-set: pass the revision you read as expected_revision; 0 means "only if absent". A stale revision makes the server answer 409 and the SDK raise ConflictError with code revision_conflict. tests/test_integration.py::test_memory_survives_daemon_restart_and_checks_revision writes with expected_revision=0, gets revision 1, sees the second expected_revision=0 write rejected, restarts the daemon and reads the value back at revision 1. update is the read-modify-write loop most handlers want; it raises ConflictError only after attempts conflicts in a row.

    TTL: ttl_seconds makes the key expire. An expired key reads as not found and disappears from listings, and its expiry produces no change-feed event (tests/test_retrieval_contract.py::test_change_feed_cursor_retention_and_ttl_expiry_semantics).

    Listing: await scope.keys(prefix=None, cursor=None, limit=None, kind="value") returns one ascending page (KeyPage.keys, next_cursor); await scope.list_keys(prefix=None, kind="value") follows the cursors and raises ValueError rather than truncating past max_keys (default 100000). kind="vector" lists vector keys.

    Vector memory

    Vectors live beside values under the same scopes, with their own revision per key. There is no app.memory.vector attribute; the methods are on MemoryScope and forwarded by Memory. The SDK ships no embedding provider in this module: you pass the embedding. Adapted from examples/python/memory_lab/agent.py, which uses fixture vectors:

    from __future__ import annotations

from dataclasses import asdict

from atfgraph import Agent

app = Agent(node_id="memory-lab", version="1.0.0")


@app.traversal()
async def vector_lookup(session_id: str) -> dict:
    scoped = app.memory.session(session_id)
    await scoped.set_vector("blue", [1.0, 0.0, 0.0], {"colour": "blue"})
    await scoped.set_vector("red", [0.0, 1.0, 0.0], {"colour": "red"})
    matches = await scoped.similarity_search([1.0, 0.0, 0.0], top_k=1)
    return {"matches": [asdict(match) for match in matches]}

    Rules enforced client-side before any request (python/atfgraph/retrieval.py) and by the server:

    MethodConstraints
    set_vector(key, embedding, metadata=None, expected_revision=None)1 to 4096 finite numbers, not the zero vector, numpy arrays accepted via tolist(); metadata must be a dict. Returns the vector revision.
    get_vector(key)VectorValue with found, embedding, metadata, dimension, revision.
    delete_vector(key, expected_revision=None)bool; the tombstone keeps the revision counting upward.
    similarity_search(query, top_k=10, filters=None, min_score=None)Cosine similarity over this scope's vectors of the query's dimension; top_k 1 to 100; filters are exact matches on top-level metadata keys; min_score in -1 to 1. Returns List[VectorMatch] (key, score, metadata, revision).
    search(query, ...)Same, as a SearchResult with scanned, dimension and strategy: linear (exact scan; always on SQLite and on PostgreSQL without a vector index for that dimension) or hnsw (a migrated PostgreSQL vector index, approximate).

    tests/test_memory_retrieval.py::test_real_daemon_vectors_listing_and_changes runs these against atfgraphd: two vectors, a ranked search, a metadata filter, a rejected zero vector (invalid_vector), a stale expected_revision (ConflictError), and vector listing. For text retrieval with server-side chunking and BM25 use app.knowledge instead (05-knowledge.md); vector memory is for embeddings you already have.

    Change feeds

    Every set and delete, of values and vectors, appends to a durable per-namespace feed with gap-free sequences. Three ways to consume it:

    • await scope.changes(after=0, limit=None, prefix=None) returns a ChangePage (items, next_cursor, oldest_sequence).
    • scope.watch("user:*", after=0, interval=0.25, stop=None) is an async iterator that polls the feed and yields MemoryChangeEvents matching shell-style patterns.
    • @app.on_change(patterns, scope=None, after=0, interval=0.25) registers a handler that serve drives for the worker's lifetime. It is the same as @app.memory.on_change.

    From examples/python/memory_lab/agent.py:

    from __future__ import annotations

from collections import deque

from atfgraph import Agent

app = Agent(node_id="memory-lab", version="1.0.0")
events = deque(maxlen=100)


@app.memory.on_change("memory-lab.*", scope="global")
async def changed(event):
    events.append({"key": event.key, "action": event.action})


@app.traversal()
async def emit_change(value: str) -> dict:
    await app.memory.global_scope().set("memory-lab.signal", value)
    return {"accepted": True, "note": "Poll recent_changes for asynchronous delivery."}


@app.skill()
def recent_changes() -> dict:
    return {"events": list(events)}

    A MemoryChangeEvent has sequence, scope, scope_id, key, kind (value or vector), action (set or delete), revision, principal, created_at and value. value is carried only for value sets whose canonical JSON is at most 65536 bytes; otherwise value_omitted is True and you re-read the key. Vector events never carry a value. Retention is 30 days; oldest_sequence is the floor to compare a saved cursor against. Handlers may be sync or async; a handler exception stops the listener group and propagates out of serve (test_change_feed_watch_and_subscriptions). The handler function is returned unchanged, so changed(event) is still callable in tests.

    Memory from outside a worker

    Client.memory_read/memory_write/memory_delete(scope, key, ..., session_id=, actor_id=, root_id=) are the typed calls the scopes are built on, for scripts and tests. Memory(lambda: client) and MemoryScope(lambda: client, "session", session_id="...") give the same facade over a bare Client, which is how tests/test_memory_retrieval.py drives the real daemon.

    What a worker credential may reach

    Inside a handler every memory request carries the task's task_id and lease_token (Client._execution_authority), so the server resolves the inherited session and root for the running traversal. Outside a traversal the same call carries no lease and is judged on the caller's own credential. python/atfgraph/agent.py states the rule for listeners: "a listener outside a traversal needs standalone memory permission; worker-only credentials cannot monitor unrelated traversals."

    Not verified: the exact server responses a worker-only credential receives when it reads another traversal's session or workflow memory, or runs on_change outside a traversal. The tests cited on this page run in loopback development mode, where the principal holds admin, invoke and worker roles; verifying the boundary needs a graph server with API keys and access policies configured as in 13-identity-credentials-and-access.md.
