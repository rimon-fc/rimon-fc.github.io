Type to search.

    Calling other nodes and fanning out

    By the end of this page you will be able to call any capability on any registered node from inside a handler, fan out many calls with asyncio.gather without deadlocking a small worker, report durable progress, react to a cancel, and let the graph server retry a step. It requires only the SDK and a running graph server; the nested_concurrency example runs with nothing else configured, and the one snippet taken from features/resilience is marked where it needs the example's fixture provider.

    traverse, call and submit

    Three methods on Agent submit a traverser (python/atfgraph/agent.py):

    MethodReturnsUse
    await app.traverse(target, **input)the child's outputCall and wait. Also accepts one positional dict: app.traverse("fanout.square", {"n": 3}). Mixing both raises TypeError.
    await app.call(target, ...)sameRetained name for traverse.
    await app.submit(target, input)HandleSubmit without waiting; wait later with handle.result().

    A target without a dot is resolved against the node's own label ("square" becomes "fanout.square"). Cross-node calls are the same call with another label: await app.traverse("pricing.quote", fare="Y") reaches whatever node registered pricing, subject to the server's access policies (13-identity-credentials-and-access.md). Pin a version with submit(..., version="1.0.0").

    Inside a handler the call is a nested child of the current step: submit reads the ExecutionContext and sends parent_step_id, the parent's parent_lease_token, and an operation_key. The child inherits the root and the session, the server records an edge from the parent step to it, and the parent's worker is woken so it claims the child promptly. Outside a handler (a script, a test) the same methods submit an ordinary root traverser through app.client.

    The module-level from atfgraph import traverse does the same through the Agent held by the current ExecutionContext.

    How a cross-node call travels

    Cross-node calls go through the graph server, always. There is no node-to-node connection and no inbound port on any node. The path one call takes:

    1. Inside a handler on node A you write await app.traverse("pricing.quote", fare="Y"). A target without a dot means this node; with a label it means whichever node registered pricing.
    2. The SDK submits a child traverser to the server carrying the parent step id, the parent's lease token and an operation key. The server records an edge from the parent step to the child, applies access policies (may this principal call this capability, how often), and queues the task for the pricing label.
    3. Node B's worker, which has been claiming work from the server all along as an outbound worker, takes the task under a lease, runs quote, and completes it back to the server.
    4. The server wakes node A's handler with the result. The child inherits the root and the session, so memory and the usage ledger line up.

    The server is the control plane and the execution gateway at once. Nodes never trust each other; they trust the server, which authenticates each call, enforces policy, leases the work, retries it when the handler raises RetryableError, requeues it when a lease expires, and writes every edge down.

    Skills and traversals on other nodes are called the same way. Both are capabilities addressed as label.capability. The difference is inside the callee: a skill is a leaf; a traversal may call further capabilities and models and becomes a subtree on the path. Whether the callee runs on your node or another is invisible to the caller apart from the label.

    Fan out with asyncio.gather

    Adapted from examples/python/nested_concurrency/agent.py. Each app.traverse is one child step; gather runs a batch concurrently and returns outputs in order.

    from __future__ import annotations

import asyncio

from atfgraph import Agent

app = Agent(node_id="fanout", version="1.0.0", capacity=4)


@app.skill()
async def square(n: int) -> dict:
    await asyncio.sleep(0.05)
    return {"n": n, "square": n * n}


@app.traversal()
async def fan_out(count: int = 6, batch: int = 3) -> dict:
    results = []
    for start in range(0, count, batch):
        chunk = list(range(start, min(start + batch, count)))
        squares = await asyncio.gather(*[app.traverse("fanout.square", n=n) for n in chunk])
        results.extend(s["square"] for s in squares)
        await app.progress({"completed": len(results), "of": count})
    return {"squares": results, "sum": sum(results)}

    tests/python_test_examples.py runs this with count=6, batch=3 and asserts {"squares": [0, 1, 4, 9, 16, 25], "sum": 55, ...} and exactly two progress events. Every square is a step under fan_out on the path; handle.path() returns them all.

    A DAG across nodes

    Nothing declares the graph. The shape comes from await and asyncio.gather inside a handler, and the server records what ran. Here three supplier searches on three nodes run in parallel, a ranking waits for all of them, and a hold depends on the ranking:

                     ┌── fares.search ──┐
trip.plan ───────┼── hotels.search ─┼──► trip.rank ──► fares.hold
                 └── weather.today ─┘

    The orchestrator:

    # trip_node.py
import asyncio

from atfgraph import Agent

app = Agent(node_id="trip", version="1.0.0", capacity=2)


@app.skill()
async def rank(fares: dict, hotels: dict, weather: dict) -> dict:
    best = min(fares["offers"], key=lambda offer: offer["total"])
    return {"fare": best, "hotel": hotels["properties"][0], "note": weather["summary"]}


@app.traversal()
async def plan(origin: str, dest: str, date: str, nights: int = 3) -> dict:
    # Level 1: three independent calls to three nodes, one child step each.
    fares, hotels, weather = await asyncio.gather(
        app.traverse("fares.search", origin=origin, dest=dest, date=date),
        app.traverse("hotels.search", city=dest, checkin=date, nights=nights),
        app.traverse("weather.today", city=dest),
    )
    await app.progress({"stage": "searched", "offers": len(fares["offers"])})

    # Level 2: depends on all three.
    choice = await app.traverse("trip.rank", fares=fares, hotels=hotels, weather=weather)

    # Level 3: depends on the ranking.
    held = await app.traverse("fares.hold", offer_id=choice["fare"]["offer_id"])
    return {"choice": choice, "hold": held, "requires_review": True}


if __name__ == "__main__":
    app.run()

    Run each node as its own worker against the same graph server, then start the root from anywhere:

    python -m atfgraph.worker --module fares_node:app
python -m atfgraph.worker --module hotels_node:app
python -m atfgraph.worker --module weather_node:app
python -m atfgraph.worker --module trip_node:app --capacity 2
atfg traverse trip.plan --in '{"origin": "BNE", "dest": "SYD", "date": "2026-10-03"}'

    What the server does with it:

    • Each app.traverse inside plan carries the parent step id and lease token, so the server records an edge from plan to that child. The path shows plan with six children, three of them concurrent; atfg path <id> prints the tree.
    • The three searches run on whichever workers own fares, hotels and weather. The orchestrator never knows their addresses. Access policies decide whether trip may call them (13-identity-credentials-and-access.md).
    • While plan waits, its worker releases the handler permit (next section), so this runs with --capacity 1 without deadlock even though trip.rank lands on the same worker as plan.
    • If fares.hold raises RetryableError and the capability declares max_attempts, the server retries that step alone. Cancelling the root cancels every child still running.

    The shapes a path can take

    In DAG tools you declare the graph and an orchestrator walks it. In ATFGraph the graph is traced, not declared: the code of each traversal decides at run time what to call, and the server records what happened. The same primitives give the classic shapes:

    ShapeHow you write itWhat the path shows
    Sequencea = await app.traverse(...), then b = await app.traverse(..., a)A chain of child steps
    Fan-out, fan-inawait asyncio.gather(*[app.traverse(...) for x in items])Parallel children under one parent, outputs in order
    Conditional branchAn if, or a @app.decision() whose structured answer carries confidenceOnly the taken branch exists as steps
    Dynamic routingapp.ai(..., tools="self") or tools="discover" lets the model choose the next capabilityOne child step per tool call
    RetryRetryableError with max_attemptsAttempts on the same step
    Pauseawait app.request_approval(...)The traverser waits, resumes on the decision
    Scheduled or event starttriggers=[ScheduleTrigger(...)] or @on_schedule on a capabilityA traverser with no caller
    Composition across teamsRouters per desk on one node, or one node per teamexamples/python/co_consult: one root, three parallel desks

    Two properties make deep graphs safe. Durability: every step is a server-side record with attempts and leases, so a worker dying mid-fan-out loses only its in-flight steps and completed children stay. Deadlock avoidance: a parent waiting on children releases its permit, so a small worker can execute a large tree.

    When the DAG is not known in advance

    examples/python/research_path is the version where a model draws the graph. A planning decision returns tasks with dependencies, the example computes parallelizable_groups by topological level and refuses a cycle, and the scheduler is five lines:

    for level in plan["parallelizable_groups"]:
    batch = await asyncio.gather(*(
        app.call("research_path.execute_research_task",
                 task=by_id[key],
                 dependencies=[results[dep] for dep in by_id[key]["dependencies"]])
        for key in level))
    results.update({item["task_id"]: item for item in batch})

    Level by level, everything in a level runs concurrently, and each task receives the outputs of the tasks it depends on. Replace the hard-coded target with a discovered one (10-multi-node.md) and each task can land on a different node.

    Capacity and deadlock avoidance

    A worker holds capacity handler permits (default 8, --capacity on the CLI). Without care, a parent that waits for a child on a worker with one permit would wait forever: the child can only run on that permit. python/atfgraph/worker.py avoids this in waiting_on_child:

    1. When a handler's first traverse starts waiting, the worker calls worker_suspend on the server and releases the permit. Concurrent waits inside one handler count as one release.
    2. When its last wait ends, the worker reacquires a permit and calls worker_resume, retrying while the server answers 429 capacity_exhausted.
    3. At most max_waiting handlers may be in the released state (default capacity * 4, --max-waiting on the CLI). Beyond that a parent keeps its permit and simply waits (tests/python_test_worker.py::test_bounded_waiting_keeps_permit_beyond_max_waiting).

    So the example above runs to completion with --capacity 1, which is how tests/python_test_examples.py runs it and how tests/test_integration.py::test_python_worker_nested_call_at_capacity_one runs it against the real daemon:

    .venv/bin/python -m atfgraph.worker --module examples.python.nested_concurrency.agent:app --capacity 1
.venv/bin/python -m examples.python.nested_concurrency.call

    Two related server rules to know when reasoning about throughput: root turns submitted with the same session_id run one at a time, but their children are not held back (test_root_session_turns_are_serialized_children_bypass); and a traverser whose lease expires is requeued and a late completion from the old lease is rejected (test_lease_expiry_requeues_and_stale_result_is_discarded).

    Progress events

    await app.progress(data) records a durable progress event on the current task's event log; await app.note("text", tags=["phase"]) is the same call with {"note": ..., "tags": [...]}. Both need an ExecutionContext and the task's lease, so they only work inside a handler. Read them back from a Handle:

    from __future__ import annotations

import asyncio
import os

from atfgraph import Client


async def main() -> None:
    async with Client(os.getenv("ATFGRAPH_SERVER")) as client:
        handle = await client.submit("fanout.fan_out", {"count": 6, "batch": 3})
        async for event in handle.events():
            print(f"event {event.sequence:>3} {event.type:<10} {event.data}")
        print("result", await handle.result(timeout=120))
        path = await handle.path()
        print(f"path: {len(path.items)} steps under root {path.root_id}")


if __name__ == "__main__":
    asyncio.run(main())

    This is examples/python/nested_concurrency/call.py without its cancel section. handle.events() streams the event log over SSE and ends at the traverser's terminal event; handle.event_log() returns the snapshot as a list. A progress payload arrives as event.data["data"], which is what the tests assert. Usage records from app.ai land on the same log as progress events with a usage key (14-observability.md).

    Cancellation

    await handle.cancel() (or atfg cancel) asks the server to cancel a traverser; the server cancels its children too (test_cancel_propagates_to_children). The worker learns of it on the next lease renew, sets the context's cancel event and cancels the handler task. A handler has two ways to observe that, both from examples/python/nested_concurrency/agent.py:

    from __future__ import annotations

import asyncio

from atfgraph import Agent

app = Agent(node_id="fanout", version="1.0.0")


@app.skill(timeout_seconds=600)
async def slow_step(seconds: float) -> dict:
    """Sleeps in small slices so a server cancel interrupts it promptly."""
    waited = 0.0
    while waited < seconds:
        if app.cancel_requested():
            break
        await asyncio.sleep(0.1)
        waited += 0.1
    return {"waited": round(waited, 1)}


@app.traversal(timeout_seconds=600)
async def long_parent(seconds: float = 30) -> dict:
    child = await app.traverse("fanout.slow_step", seconds=seconds)
    return {"child": child}

    app.cancel_requested() is a cooperative check for loops; an await inside the handler will also raise asyncio.CancelledError once the worker cancels the task. Either way the worker records nothing further for a cancelled task, and the caller's handle.result() raises TraversalCancelled. A progress call that races with the cancel can fail with ConflictError; examples/python/features/resilience/agent.py catches it and stops. Sync handlers cannot be interrupted: the thread runs to its end and its result is dropped.

    Retries

    A handler exception is terminal by default: the worker completes the task with {"code": <exception class>, "retryable": false} and the traverser fails. To let the server schedule another attempt, raise RetryableError (or HandlerError(..., retryable=True)) and give the capability a budget with max_attempts. From examples/python/nested_concurrency/agent.py:

    from atfgraph import Agent, RetryableError, current_context

app = Agent(node_id="fanout", version="1.0.0")


@app.skill(max_attempts=3)
async def flaky_step(succeed_on_attempt: int = 2) -> dict:
    """Fails with a retryable error until the server has scheduled ``succeed_on_attempt`` attempts."""
    ctx = current_context()
    if ctx.attempt < succeed_on_attempt:
        raise RetryableError(f"attempt {ctx.attempt} failed on purpose")
    return {"attempt": ctx.attempt}

    What the tests show (tests/python_test_examples.py, tests/test_feature_examples_extended.py):

    • ctx.attempt starts at 1 and increments per scheduled attempt; the recorded step has one entry per attempt in PathStep.attempts, the first marked retryable: true.
    • The event log carries a requeued event per retry with the error envelope, and client.get(id).raw["attempt"] and raw["max_attempts"] show the counters.
    • When the budget is spent the traverser fails with the last error's code (TraversalFailed.code).
    • Retries of a parent do not duplicate its children: ExecutionContext.operation_key derives a stable key from the target, the input and the call count, so the server returns the existing child (test_operation_keys_are_stable_across_parent_retries).

    examples/python/features/resilience/agent.py applies the same pattern to a model call: a ModelError from the provider is re-raised as RetryableError, and a bad request that the provider would reject again is left as a plain exception so it fails once. That example needs its fixture provider running (python -m examples.python.features.resilience.fixture_model --port 18899 and ATFGRAPH_MODEL_URL/ATFGRAPH_MODEL_NAME pointing at it); without a provider app.ai raises ModelNotConfigured.

    Timeouts

    Three different clocks apply, and they fail differently:

    WhereSet byWhat happens
    Handler budgettimeout_seconds on the capability (default 300)The worker stops the handler with asyncio.wait_for and completes the task failed with code handler_timeout, retryable: false.
    Server deadlineThe graph server, from the same registered budgetIf the worker itself is gone, the server's sweep marks the traverser timed_out; callers see TraversalTimedOut.
    Client waittimeout= on app.traverse, handle.result, client.traverse, client.waitRaises WaitTimeout in the caller after polling with jittered backoff. The traverser keeps running; cancel it if you no longer want it.

    tests/test_feature_examples_extended.py::test_resilience_example_stops_a_stalled_call_at_its_budget submits disruption.stalled_note (timeout_seconds=2) against a provider that stalls for 30 seconds and asserts the status is failed or timed_out with code handler_timeout or timed_out, well inside 20 seconds. Inside a nested app.traverse(..., timeout=...) the WaitTimeout propagates out of the parent handler like any other exception and fails the parent unless you catch it.
