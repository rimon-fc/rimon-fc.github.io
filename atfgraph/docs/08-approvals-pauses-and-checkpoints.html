    Approvals, pauses and checkpoints

    By the end of this page you will be able to stop a traversal for a human decision without holding a worker, decide it from another program, have the handler continue with that decision after a restart of both the server and the worker, and use checkpoints so the work done before the pause runs exactly once. It requires only the SDK and a running graph server; the features/approvals example runs against invented fixture data with no provider configured.

    What a pause is

    await app.request_approval(prompt, operation_key=..., checkpoint=...) (python/atfgraph/agent.py) posts the prompt and checkpoint to POST /api/v2/approvals with the task's lease. The server stores the approval as pending, closes the lease and moves the traverser to the waiting state. Inside the worker the call raises an internal _TraversalPaused control exception, so the handler stops right there and its worker permit is released; python/atfgraph/worker.py counts it as stats.paused and does not complete the task. No process holds anything while the reviewer thinks.

    When someone decides, the server queues a continuation for the same traverser id. The handler runs again from the top with a fresh lease and current_context().attempt increased by one; on that attempt request_approval with the same operation_key returns the stored decision instead of pausing. app.pause(...) is a retained name for the same method; it is a durable server-side pause, never an in-process wait.

    Three server rules shape how you write the handler (docs/feature-examples-evidence.md, verified by the tests cited below):

    • An approval is keyed by (traverser, operation_key). Requesting the same key again with a different prompt is 409 approval_conflict, so the prompt on the replay must be byte-identical.
    • A decision is approved or rejected. Deciding the same way twice is idempotent; a different second decision is 409 approval_decided.
    • The continuation raises max_attempts by one, so it is not charged to the capability's failure budget.

    Checkpoints make the replay safe

    Everything the handler does before the pause runs again on the continuation unless you stop it. app.save_checkpoint(name, value, expected_revision=None) stores a JSON value on the current traverser (POST /api/v2/traversers/{id}/checkpoints/{name}) and returns the revision; app.load_checkpoint(name, default=None) reads it back or returns the default when it does not exist. expected_revision=0 means "create only", so a racing replay conflicts instead of preparing the case twice.

    The pattern from examples/python/features/approvals/agent.py: load the checkpoint; if it is missing, do the preparatory work (here a recorded child step) and save it; build the prompt only from the checkpoint; then pause.

    from __future__ import annotations

from typing import Dict

from atfgraph import Agent, HandlerError, current_context

app = Agent(node_id="refunds", version="1.0.0", description="Refund desk with a durable approval pause", capacity=2)

AUTO_LIMIT_AUD = 200.0
CASE = "refund case"

FIXTURE_TICKETS: Dict[str, dict] = {
    "QF-4417": {"route": "BNE-SYD", "fare_aud": 612.40, "fare_basis": "flex", "flown": False},
    "NZ-0882": {"route": "AKL-QUN", "fare_aud": 189.00, "fare_basis": "saver", "flown": False},
}


@app.skill()
async def assess(ticket: str) -> dict:
    record = FIXTURE_TICKETS.get(ticket.upper())
    if record is None:
        raise HandlerError(f"unknown ticket {ticket!r}", code="ticket_not_found")
    return {"ticket": ticket.upper(), **record}


@app.traversal(timeout_seconds=3600)
async def request_refund(ticket: str, amount_aud: float, reason: str = "schedule change") -> dict:
    attempt = current_context().attempt
    case = await app.load_checkpoint(CASE)
    if case is None:
        ticket_record = await app.traverse("refunds.assess", ticket=ticket)
        case = {
            "ticket": ticket_record["ticket"],
            "route": ticket_record["route"],
            "fare_aud": ticket_record["fare_aud"],
            "amount_aud": round(float(amount_aud), 2),
            "reason": reason,
            "prepared_on_attempt": attempt,
        }
        await app.save_checkpoint(CASE, case, expected_revision=0)

    if case["amount_aud"] <= AUTO_LIMIT_AUD:
        return {"ticket": case["ticket"], "amount_aud": case["amount_aud"], "status": "approved", "decided_by": "desk-policy", "attempts": attempt}

    decision = await app.request_approval(
        {"question": f"Refund {case['amount_aud']} AUD on {case['ticket']} ({case['route']})?", "case": case, "auto_limit_aud": AUTO_LIMIT_AUD},
        operation_key=f"refund:{case['ticket']}",
        checkpoint=case,
    )
    return {
        "ticket": case["ticket"],
        "amount_aud": case["amount_aud"],
        "status": decision["status"],
        "decided_by": decision.get("decided_by"),
        "response": decision.get("response"),
        "attempts": current_context().attempt,
        "prepared_on_attempt": case["prepared_on_attempt"],
    }

    tests/test_feature_examples_extended.py::test_approval_example_pauses_across_a_restart_and_prepares_its_case_once runs this against the real daemon and pins the outcome: the result reports attempts == 2 and prepared_on_attempt == 1, and the path contains exactly one refunds.assess step. Without the checkpoint the child step would run twice and appear twice.

    The checkpoint= argument on request_approval is separate from save_checkpoint: it is stored with the approval so the reviewer can see the state the question was asked about, and it is returned in list_approvals(). The two are usually the same object, as above.

    timeout_seconds=3600 on the traversal is the capability budget for one attempt; the pause itself is not charged against it because the attempt ends when the lease closes.

    What the decision looks like

    The dict request_approval returns on the continuation is the approval record: status (approved or rejected), decided_by, response (whatever the decider passed), operation_key, prompt, checkpoint, id and traverser_id. A rejection also resumes the handler, so your code decides what a rejection means; the example returns it as status: "rejected" and succeeds.

    Deciding out of band

    The reviewer is another program with a Client. list_approvals() returns the pending records, get_approval(id) one record, and decide_approval(id, decision, response=None) records the decision. Adapted from examples/python/features/approvals/review.py:

    from __future__ import annotations

import asyncio
import json
import os

from atfgraph import Client


async def wait_for_status(client: Client, traverser_id: str, status: str, seconds: float = 30.0) -> None:
    deadline = asyncio.get_running_loop().time() + seconds
    while asyncio.get_running_loop().time() < deadline:
        current = await client.get(traverser_id)
        if current.status == status:
            return
        if current.is_terminal:
            raise SystemExit(f"traverser {traverser_id} reached {current.status} before {status}: {current.error}")
        await asyncio.sleep(0.05)
    raise SystemExit(f"traverser {traverser_id} never reached {status}")


async def main() -> None:
    async with Client(os.getenv("ATFGRAPH_SERVER")) as client:
        handle = await client.submit("refunds.request_refund", {"ticket": "QF-4417", "amount_aud": 480.0, "reason": "cancelled leg"})
        await wait_for_status(client, handle.id, "waiting")
        pending = [a for a in await client.list_approvals() if a["traverser_id"] == handle.id]
        approval = pending[0]
        print("prompt    ", json.dumps(approval["prompt"]["question"]))
        print("checkpoint", json.dumps(approval["checkpoint"], sort_keys=True))
        decided = await client.decide_approval(approval["id"], "approved", {"note": "verified against the disruption log"})
        print("decided   ", decided["status"], "by", decided["decided_by"])
        result = await handle.result(timeout=60)
        print("result", json.dumps(result, sort_keys=True))
        for step in (await handle.path()).items:
            print(f"  {step.target:<26} {step.status}")


if __name__ == "__main__":
    asyncio.run(main())

    waiting is not terminal, so handle.result() keeps polling through the pause and returns once the continuation finishes. Client.wait and Client.traverse behave the same way; a timeout= on them bounds the whole wait including the human.

    The atfg command reference (../cli-reference.md) has no approval command; atfg ps shows the traverser in waiting, but the decision itself is made through Client.decide_approval, the POST /api/v2/approvals/{id}/decide operation, or the web console's Policies page (../howto-web-console.md). Decisions are owner or admin operations; a worker-only credential cannot decide.

    Run the example from this repository's root with a graph server running:

    python -m atfgraph.worker --module examples.python.features.approvals.agent:app
python -m examples.python.features.approvals.review --ticket QF-4417 --amount 480
python -m examples.python.features.approvals.review --ticket QF-4417 --amount 480 --decision rejected
python -m examples.python.features.approvals.review --ticket NZ-0882 --amount 150

    The third run is under the desk limit and never creates an approval (test_approval_example_settles_small_refunds_rejects_and_refuses_over_fare asserts list_approvals() == [] afterwards).

    Surviving a restart

    The pause is server state, not worker state. tests/test_runtime_journeys.py::test_approval_continues_after_server_and_worker_restart stops the daemon and the worker while the approval is pending, starts a new daemon on the same SQLite file, decides through a fresh Client, starts the worker again, and sees the traverser reach succeeded with the decision and the checkpoint intact. Its handler is the minimal form of the pattern:

    from __future__ import annotations

from atfgraph import Agent

app = Agent(node_id="approval", capacity=1)


@app.skill()
async def reviewed() -> dict:
    saved = await app.load_checkpoint("travel brief")
    if saved is None:
        saved = {"origin": "BNE", "revision": 1}
        await app.save_checkpoint("travel brief", saved, expected_revision=0)
    decision = await app.request_approval("Review this plan", operation_key="review", checkpoint=saved)
    return {"decision": decision["status"], "saved": saved}

    Two consequences follow. First, a worker that is deploying a new version while approvals are pending must still serve the same label and version, because a continuation is claimed by (label, version) like any other task. Second, the handler code that runs on the continuation is whatever is deployed then; keep the pre-pause work behind the checkpoint so a code change does not repeat side effects.

    Checkpoints without a pause

    Checkpoints are a per-traverser store you can use on their own. The typical case is a handler with max_attempts > 1 that performs an external side effect: save a marker before the call, check it on retry. Reading a checkpoint from outside the handler is Client.get_checkpoint(traverser_id, name), which returns {"value": ..., "revision": ...} or raises NotFoundError; writing one requires a task lease, so Client.put_checkpoint only works inside a handler and app.save_checkpoint is the normal spelling.

    A checkpoint is scoped to one traverser. State that must outlive the traverser or be shared belongs in memory (04-sessions-and-memory.md), which has the same expected_revision compare-and-set.
