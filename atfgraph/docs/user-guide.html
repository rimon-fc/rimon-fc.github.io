    ATFGraph vNext user guide

    Use atfg to start a graph server, install agent nodes, start traversers and inspect their paths. Use the Python SDK to write your own nodes or call a server from an application. This page is the reading order through the other guides, plus the reference tables that do not belong to any one task.

    ComponentPurposeCommand
    Graph serverRoutes work and stores pathsatfgraphd
    CLIStarts servers and interacts with agent nodesatfg
    Python workerRuns your node and connects to the serverpython -m atfgraph.worker

    Vocabulary: a graph server owns the graph; an agent node registers under a label with a version and a set of traversals (LLM-backed functions) and skills (deterministic functions); starting one creates a traverser; the record it leaves is a path made of steps; atfg wait blocks at the barrier until the traverser is terminal. Definitions: Core concepts.

    Which side are you on?

    Consumer, SDK only. You start traversers on nodes that already run somewhere and read their results. You never keep a process of your own alive. You need a graph server URL and, off loopback, an API key. You use the Python client, atfg traverse, atfg wait, atfg path, or the web console. You do not need Docker, a worker or a configuration file.

    export ATFGRAPH_SERVER=http://127.0.0.1:18880   # or a remote server
export ATFGRAPH_API_KEY=...                      # required off loopback
atfg ls
atfg traverse co-consult.consult --in '{"request":"A relaxed family trip to Tokyo"}' --new-session

    Builder. You write an agent node and run it as an outbound worker. The worker enrols with the graph server, claims tasks for its label and version, renews its lease while it works, streams progress and reports the result. It opens no port. It can be a worker you run (python -m atfgraph.worker, or atfg dev), an installed node (atfg install then atfg run), or a managed host started for you by a deployment target. Either way the graph server is the only inbound endpoint; nothing calls a node directly.

    CLI command table

    Global flags (every command): --server/-s (env ATFGRAPH_SERVER, default http://127.0.0.1:18880), --api-key/-k (env ATFGRAPH_API_KEY, sent as Authorization: Bearer), --json, --timeout <s> (HTTP timeout, default 30), --state-dir (env ATFGRAPH_VNEXT_HOME). Every flag of every command is in the generated CLI reference.

    --in must be a JSON object: the traversal's named inputs, unwrapped. --in-file - reads stdin.

    Exit codes

    CodeMeaning
    0Success; for traverse/wait, the traverser succeeded
    1Error: unreachable server, API error envelope (code (status): message [request id]), invalid input or config
    2Timed out waiting: still not terminal after --wait-timeout (traverse, wait), or /health did not answer in time (server start), or the daemon did not exit within --grace (server stop), or registration took longer than --wait (run)
    3The traverser reached a terminal state other than succeeded: failed, cancelled, timed_out; for deploy compose status, the observed state differs from the desired state

    Typical session

    atfg ls
ID=$(atfg traverse hello.greet --in '{"name":"Ada"}' --async)
atfg ps --status queued
atfg wait "$ID" --wait-timeout 120 || echo "exit $?"
atfg path "$ID"
atfg --json show "$ID" | jq .output

    Troubleshoot a running node

    atfg doctor
atfg server status
atfg ls
atfg ps
atfg show <traverser-id>
atfg path <traverser-id>
atfg logs <node-name> --tail 100

    If a label is missing from atfg ls, check that its worker is running and uses the same server URL and namespace as your client. Check its logs for registration or authentication errors. For a failed call, inspect the traverser and its path to identify the step that failed. The messages you may see are listed verbatim in Troubleshooting.
