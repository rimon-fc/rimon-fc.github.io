    Delegating to a coding harness

    By the end of this page you will be able to hand a task to an installed coding-agent CLI from inside a handler with app.harness, choose the provider, confine it to a working directory with tools disabled, bound its runtime, validate its answer against a schema, and read what the run left on the path. It requires the SDK, a running graph server and one of the supported CLIs installed on the worker host; the repository tests substitute a fake executable, and this page says where.

    Prerequisites: one of atfHar, claude, codex or opencode on the worker's PATH, with whatever credentials that CLI itself needs.

    When to reach for a harness

    app.harness is the heaviest thing a traversal can do. app.ai makes one model call and returns; a harness spawns a coding agent that reads, edits and creates files in a directory, runs commands, and iterates for as many turns as it needs before answering. The traversal that called it sees the answer and the metrics, not the individual edits. Use it when the task genuinely needs a coding agent: fixing a failing test, describing or refactoring a repository, generating a project from a brief. For a question that a single model call with tools can answer, use app.ai(tools="self") from 06-model-calls.md; it is cheaper, faster, and every tool call lands on the path as its own step.

    app.aiapp.harness
    Turnsone call, or a bounded tool loopas many as the CLI takes, within a wall-clock deadline
    Side effectsnone unless a tool has themedits files in cwd; run it with max_attempts=1
    On the pathone step per tool callone step, plus a progress event per CLI event
    Costrecorded automaticallyreturned on the result; you record it if you want it counted

    Install a provider

    The worker host needs the CLI on PATH; the graph server needs nothing. Credentials are the CLI's own.

    # atf-harness: the family's own runtime, a Bun application
git clone <the atf-harness repository> && cd atf-harness && bun install && bun link
atfHar --version

# claude-code: Anthropic's CLI; signs in with `claude` login or ANTHROPIC_API_KEY
npm install -g @anthropic-ai/claude-code

# codex: OpenAI's CLI; signs in with `codex` login or OPENAI_API_KEY
npm install -g @openai/codex

# opencode: its installer script from opencode.ai; brings its own provider configuration
curl -fsSL https://opencode.ai/install | bash

    Check before a paid run, from the shell or from a node:

    python -m examples.harness.python.call --doctor

    harness_doctor() looks executables up on PATH and never runs them, so available: true proves the binary is present, not that its credentials work. An absent or expired provider credential surfaces later as a failed traverser whose error message is the CLI's own report, a 401 from the model provider included.

    Not verified: the install commands for claude, codex and opencode against current releases; they are the vendors' documented commands, not something this repository runs.

    What the bridge does

    app.harness(prompt, ...) (python/atfgraph/agent.py) runs one bounded invocation of a coding-agent CLI through run_harness in python/atfgraph/harness_bridge.py. The bridge owns the process: no shell, JSON-lines output parsed into a HarnessResult, a wall-clock deadline, an output size limit, and termination of the whole process group when the traversal is cancelled or the deadline passes. Which CLI runs and how its output is read comes from a provider in python/atfgraph/harness_providers.py; providers only build argument vectors and parse events, they never spawn anything.

    Two things the bridge is not: it is not a sandbox (an explicit cwd confines the working directory, nothing more), and it never fabricates an answer. A CLI that exits non-zero, reports an error event or prints no assistant text raises HarnessFailure, and the traversal fails with that message.

    In order, one call does five things:

    1. A provider is chosen. provider= on the call, else Agent(harness_provider=...), else ATFGRAPH_HARNESS_PROVIDER, else atf-harness. The CLI must be on the worker's PATH with its own credentials; the graph server needs nothing.
    2. The bridge owns the process. The CLI starts as a child in its own process group, with no shell and no inbound port, confined to cwd=, with tools disabled unless you list them. The bridge parses the CLI's JSON-lines events as they stream.
    3. Bounds are enforced. A wall-clock timeout (300 s by default), a 4 MiB cap on combined output, and an optional max_cost_usd: the first streamed event that pushes the provider-reported cost past the cap kills the child and fails the step with harness_cost_exceeded, not retryable. Cancelling the traverser terminates the process group.
    4. Typed output if you ask. schema= appends the schema to the prompt, strips a code fence if the CLI added one, validates, and puts the object on result.parsed.
    5. What comes back. A HarnessResult with the text, the parsed object, provider, model, session id, token counts, turns, duration and cost_usd when the provider stated one. Nothing is fabricated: if the CLI never answered, the result says so.

    The run is one step on the path, the traversal that called it; every CLI event is a progress event on that step. Cost is returned, not recorded, because a harness run is a side effect on real files; see What comes back. Run harness traversals with max_attempts=1, since a retry would redo the edits.

    app.harness_doctor() (or the module-level harness_doctor()) reports a ProviderHealth per provider: provider, binary, available, path, restricts_tools and an install hint. It only looks executables up on PATH; it runs nothing. Both examples expose it as a skill so an operator can ask a worker what it can run, adapted from examples/python/features/harness_delegate/agent.py:

    from __future__ import annotations

from atfgraph import Agent

app = Agent(node_id="delegate", version="1.0.0", description="Harness delegation with typed results")


@app.skill()
def doctor() -> dict:
    """Which harness CLIs are available here (no process is started)."""
    return {health.provider: {"available": health.available, "binary": health.binary} for health in app.harness_doctor()}

    A Claude Code node, end to end

    A node that asks Claude Code to review a directory and return a typed answer:

    # review_node/agent.py
from typing import List

from pydantic import BaseModel

from atfgraph import Agent

app = Agent(node_id="reviewer", version="1.0.0", description="Delegates code review to Claude Code")


class Review(BaseModel):
    summary: str
    risks: List[str]
    suggested_tests: List[str]


@app.traversal(max_attempts=1, timeout_seconds=900)  # never retry a harness run
async def review(path: str) -> Review:
    result = await app.harness(
        "Review the code in this directory. Name the main risks and the tests you would add.",
        provider="claude-code",   # the `claude` CLI on the worker's PATH, signed in
        cwd=path,                 # confined to this directory
        tools=[],                 # all Claude Code built-in tools off: read-only reasoning
        max_turns=6,              # Claude Code option, passed through
        schema=Review,            # the answer must parse as Review
        timeout=600,              # the bridge's wall-clock deadline; timeout_seconds above must be larger
        max_cost_usd=0.50,        # kill the run if Claude Code's streamed cost passes this
    )
    return result.parsed
    atfg install ./review_node && atfg run reviewer
atfg traverse reviewer.review --in '{"path": "/Users/you/some-project"}'

    The worker spawns claude with tools disabled and --max-turns 6, working in path. Every event Claude Code prints becomes a progress event on the step, visible live in the Console. The final text is validated against Review. The cost Claude Code reports is on result.cost_usd; if the cap is crossed the child is killed and the step fails with harness_cost_exceeded. Nothing runs if claude is not on PATH; app.harness_doctor() tells you beforehand.

    Letting Claude Code edit is the same call with tools on and a supervised shape: a first run with tools=[] produces a plan, request_approval pauses the traversal until someone approves in the Console, and a second run with permission_mode="auto" applies the plan and runs the tests (Supervised writes).

    Claude Code specifics from the provider table: it signs in with claude login or ANTHROPIC_API_KEY; tools=[] maps to --tools ""; permission_mode=, max_turns=, system_prompt= and resume= pass straight through; it reports cumulative total_cost_usd, so the cost cap works per event.

    Delegate with typed output

    schema= (a Pydantic model or a JSON Schema dict) appends "Return only a JSON value matching this schema" plus the schema to the prompt, strips a Markdown code fence from the answer if the CLI wrapped it in one, validates the JSON and stores the instance on result.parsed. Output that does not validate raises HarnessFailure("Harness output did not match the requested schema"). From examples/python/features/harness_delegate/agent.py:

    from __future__ import annotations

import os
from typing import List, Optional

from pydantic import BaseModel

from atfgraph import Agent

app = Agent(node_id="delegate", version="1.0.0", description="Harness delegation with typed results")


class DirectorySummary(BaseModel):
    purpose: str
    languages: List[str]
    entry_points: List[str]


@app.traversal(timeout_seconds=900)
async def describe_directory(path: str, provider: Optional[str] = None, model: Optional[str] = None) -> DirectorySummary:
    """Ask a coding agent to describe ``path``; the result must match ``DirectorySummary``."""
    if not os.path.isdir(path):
        raise ValueError(f"{path!r} is not a directory")
    result = await app.harness(
        "Describe this directory: its purpose, the programming languages used and the entry points.",
        provider=provider,
        model=model,
        cwd=path,
        schema=DirectorySummary,
        timeout=600,
    )
    return result.parsed

    Note the two timeouts. timeout=600 is the harness deadline enforced by the bridge; timeout_seconds=900 on the traversal is the capability's own budget on the graph server and must be the larger of the two, or the server times the step out while the CLI is still running. tests/test_authoring_parity.py::test_agent_harness_validates_schema_and_reports_doctor runs this traversal against a fake atfHar, checks the fenced JSON is parsed, and checks that a wrong-shaped answer raises.

    Working directory and tools

    cwd= is required. It comes from the call, or from Agent(harness_cwd=...); with neither, app.harness raises ValueError("harness requires an explicit cwd") before anything runs. The directory must exist. The CLI's working directory is set to it and, for the providers that take one, it is also passed as a flag (--cwd, -C, --dir).

    Tools are disabled unless you list them. tools=["Read", "Grep"] passes exactly those names; a name containing a comma or starting with - raises ValueError. The bridge cannot make opencode drop its tools, so that provider refuses to run without allow_default_tools=True.

    Timeouts, budgets and cancellation

    OptionDefaultEffect
    timeout300 sWall-clock deadline; raises HarnessFailure("Harness exceeded its execution deadline")
    max_output_bytes4 MiBCombined stdout and stderr cap; exceeding it raises HarnessFailure
    modelnonePassed to the CLI's model flag
    session_dir / resumenonePersistent sessions need an explicit directory; resume without one raises
    envnoneExtra environment variables for the child process only
    keep_eventsFalseKeep every raw JSON event on result.events
    binaryprovider defaultAlternative executable name; how the tests point at a fake CLI
    max_cost_usdnone, or ATFGRAPH_HARNESS_MAX_COST_USDUSD cap on the harness itself; when the provider's streamed cost crosses it the child is killed and the step fails with harness_cost_exceeded

    The cost cap is enforced while the harness streams: Claude Code reports a cumulative total_cost_usd on every event, OpenCode a cost per finished step and Codex a cost per completed turn, and the bridge kills the process group (SIGTERM, then SIGKILL after five seconds) the moment the running total exceeds max_cost_usd. The step fails with HarnessCostExceeded, a HandlerError with code="harness_cost_exceeded", retryable=False and the attributes cost_usd, cap, turns, provider, killed and partial_text; the message ends with the last two kilobytes of assistant text so the path shows what was produced before the cut. Providers that report no cost per event (gemini, atf-harness) are checked once on the final result with the same code. This cap is separate from the graph server's budgets: a budget refuses the next admission for a principal, node or target over a window; the harness cap stops this process.

    When the traversal is cancelled from the graph server, the awaiting coroutine is cancelled and the bridge's finally block sends SIGTERM to the process group, then SIGKILL after two seconds. Nothing of the partial output is returned.

    The harness example shows the strict configuration: no tools, one attempt, a fixed deadline. Adapted from examples/harness/python/agent.py:

    from __future__ import annotations

import os
from typing import Optional

from atfgraph import Agent

app = Agent(node_id="harness-example", version="0.1.0", tags=["harness"])


@app.traversal(max_attempts=1, timeout_seconds=180)
async def answer(prompt: str, model: str, cwd: str, provider: Optional[str] = None, timeout: float = 120.0) -> dict:
    if not os.path.isdir(cwd):
        raise ValueError(f"{cwd!r} is not an existing directory")
    result = await app.harness(
        prompt,
        provider=provider,
        model=model,
        cwd=cwd,
        tools=[],
        timeout=float(timeout),
    )
    return {
        "text": result.text,
        "provider": result.provider,
        "model": result.model,
        "input_tokens": result.input_tokens,
        "output_tokens": result.output_tokens,
        "total_tokens": result.total_tokens,
        "cost_usd": result.cost_usd,
        "session_id": result.session_id,
        "turns": result.turns,
        "duration_ms": result.duration_ms,
    }

    max_attempts=1 matters here: a harness run is a side effect on a real directory, and a retry would run it again. The shipped example reads model and cwd from ATFGRAPH_HARNESS_MODEL and ATFGRAPH_HARNESS_WORKDIR when they are not passed, and refuses with ValueError when neither is set.

    What comes back

    HarnessResult carries text (also result), provider, session_id, model, usage (a dict with input, output, cacheRead, cacheWrite), returncode, parsed, duration_ms, turns, cost_usd and events. input_tokens, output_tokens and total_tokens read the usage dict. cost_usd is only what the CLI itself reported: claude-code reports total_cost_usd, opencode sums per-step cost, atf-harness and codex report none, so it stays None (tests/test_migrated_ops_examples.py asserts "atfHar reported no price; none is invented").

    A harness run is not added to app.execution_cost() on its own. Agent.harness returns the tokens but does not call record_usage; if you want the run in the execution's cost totals and the durable usage store, record it yourself:

    from __future__ import annotations

from atfgraph import Agent, CostEntry

app = Agent(node_id="delegate", version="1.0.0")


@app.traversal(timeout_seconds=900)
async def summarize(path: str) -> dict:
    result = await app.harness("Summarize this directory in one paragraph.", cwd=path, timeout=600)
    await app.record_usage(
        CostEntry(
            model=result.model or "unknown",
            provider=result.provider,
            source="harness",
            operation="chat",
            input_tokens=result.input_tokens,
            output_tokens=result.output_tokens,
            total_tokens=result.total_tokens,
            cost_usd=result.cost_usd,
            cost_source="provider" if result.cost_usd is not None else None,
        )
    )
    return {"text": result.text, "cost": app.execution_cost()}

    CostEntry is exported from atfgraph; source="harness" is one of the values python/atfgraph/costs.py reserves for it. 14-observability.md covers where recorded usage goes.

    How a run is recorded on the path

    The run itself is one step: the traversal that called app.harness. The CLI does not appear as a child step, because nothing was submitted to the graph server for it. What is recorded, durably, is progress: for every JSON event the CLI prints, the bridge calls app.progress({"harness": {"provider": ..., "type": ...}}) on the current task. Only the provider name and event type are forwarded, never the event payload, because tool payloads can contain secrets. Pass on_event= (an async callable) to receive the same summaries in-process.

    tests/test_migrated_ops_examples.py::test_harness_example_runs_a_fixture_harness_with_no_tools_and_reports_usage runs examples/harness/python against the real daemon with a fake atfHar on PATH and pins the visible result: handle.event_log() contains progress events whose data mentions harness, the output carries session_id, provider, model and the token counts the CLI reported, and a CLI that exits 1 fails the traverser with code == "HarnessFailure". The driver in examples/harness/python/call.py prints the same event count after the result.

    atfHar end to end

    atf-harness is the default provider and the one the shipped example is built around. Three things make it work: the binary on the worker's PATH, its model configuration under ~/.atf-harness/agent/, and the credential that configuration names in the worker's environment.

    1. Configure the model. config.yml picks a role, models.yml says where that model lives and which environment variable holds its key. A Databricks Model Serving endpoint looks like this:

    # ~/.atf-harness/agent/config.yml
modelRoles:
  default: databricks/claude-sonnet-4-endpoint:max      # provider/model:variant
    # ~/.atf-harness/agent/models.yml
providers:
  databricks:
    baseUrl: https://adb-1234567890.12.azuredatabricks.net/serving-endpoints
    apiKey: DATABRICKS_TOKEN        # the NAME of a variable in the worker's environment
    models:
      - id: claude-sonnet-4-endpoint

    Not verified: the exact models.yml keys against the current atf-harness release; the two files, the provider/model:variant role form and the apiKey: <ENV_NAME> resolver are as the original project's harness guide documents them.

    2. Write the node. This is the shipped examples/harness/python/agent.py, trimmed. It exposes the harness as one traversal and a doctor skill, permits no tools, and runs one attempt:

    from __future__ import annotations

import os
from typing import Optional

from atfgraph import Agent

app = Agent(node_id="harness-example", version="0.1.0", tags=["harness"])


@app.skill()
def doctor() -> dict:
    return {h.provider: {"available": h.available, "path": h.path, "hint": h.hint} for h in app.harness_doctor()}


@app.traversal(max_attempts=1, timeout_seconds=180)
async def answer(prompt: str, model: Optional[str] = None, cwd: Optional[str] = None,
                 variant: Optional[str] = None, timeout: float = 120.0) -> dict:
    model = model or os.environ.get("ATFGRAPH_HARNESS_MODEL") or None
    cwd = cwd or os.environ.get("ATFGRAPH_HARNESS_WORKDIR") or None
    if model is None or cwd is None:
        raise ValueError("set ATFGRAPH_HARNESS_MODEL and ATFGRAPH_HARNESS_WORKDIR, or pass model= and cwd=")
    result = await app.harness(
        prompt,
        provider="atf-harness",
        model=model,
        cwd=cwd,
        tools=[],                 # explicit: no built-in tools
        variant=variant,          # atfHar --thinking; None keeps the configured variant
        timeout=float(timeout),
    )
    return {
        "text": result.text,
        "session_id": result.session_id,
        "model": result.model,
        "turns": result.turns,
        "input_tokens": result.input_tokens,
        "output_tokens": result.output_tokens,
        "cost_usd": result.cost_usd,      # None: atfHar reports no price and none is invented
        "duration_ms": result.duration_ms,
    }

    The bridge turns that call into exactly this command, prompt last after -- so it can never be read as a flag:

    atfHar --print --mode json --cwd <cwd> --no-title --model <model> [--thinking <variant>] --no-tools --no-session -- <prompt>

    --no-tools comes from the empty tools=[], --no-session from the absent session_dir. Pass tools=["read", "glob"] to allow named tools, or session_dir= to keep sessions (see the next section).

    3. Run it. The worker is what spawns atfHar, so the credential goes into the worker's shell:

    export DATABRICKS_TOKEN=dapi-your-token            # the variable models.yml names
export ATFGRAPH_HARNESS_MODEL='databricks/claude-sonnet-4-endpoint'
export ATFGRAPH_HARNESS_WORKDIR="$PWD"
python -m atfgraph.worker --module examples.harness.python.agent:app

# another terminal
python -m examples.harness.python.call --doctor
python -m examples.harness.python.call "Reply with the word ready."
atfg traverse harness-example.answer --in '{"prompt": "List the top-level files here", "variant": "max"}'

    Every JSON event atfHar prints becomes a durable progress event on the traverser ({"harness": {"provider": "atf-harness", "type": "message_end"}} and so on), which call.py counts after printing the result. A missing or expired DATABRICKS_TOKEN fails the traverser with the harness's own 401 report as error.message; doctor cannot detect that, because it only checks the binary is present.

    Differences from the original example. The node is an outbound worker, so there is no PORT; HarnessConfig(max_retries=0) became @app.traversal(max_attempts=1), enforced by the server; max_turns=1 is gone because atfHar --print runs one turn by construction; failures raise HarnessFailure instead of returning is_error=True; and progress events are new.

    Multi-turn sessions

    A harness call is one bounded invocation. To continue the same coding session across traversals, give the provider an explicit session_dir and pass the returned session_id back as resume. Without a session_dir, atf-harness runs with --no-session and resume raises ValueError. Adapted from the provider options in python/atfgraph/harness_providers.py and tests/test_authoring_parity.py:

    from __future__ import annotations

from typing import Optional

from atfgraph import Agent

app = Agent(node_id="pairing", version="1.0.0", harness_cwd="/srv/repos/checkout", harness_provider="atf-harness")

SESSIONS = "/srv/harness-sessions"   # outside the coding workspace


@app.traversal(max_attempts=1, timeout_seconds=1800)
async def step(instruction: str, session_id: Optional[str] = None) -> dict:
    result = await app.harness(
        instruction,
        session_dir=SESSIONS,
        resume=session_id,
        tools=["Read", "Grep", "Edit"],
        timeout=1200,
    )
    return {"session_id": result.session_id, "text": result.text, "turns": result.turns}

    The caller stores session_id in session memory between turns (04-sessions-and-memory.md), so a conversation with a human maps onto one coding session. codex refuses resume; claude-code and atf-harness accept it. Agent(harness_cwd=..., harness_provider=...) sets node-wide defaults so handlers only pass what varies.

    Supervised writes: plan, approve, apply

    A harness with write tools is a side effect on a real directory. The pattern that keeps a human in control uses two calls and the durable approval from 08-approvals-pauses-and-checkpoints.md: a read-only run produces a plan, a person approves it, a second run applies it.

    from __future__ import annotations

from typing import List

from pydantic import BaseModel

from atfgraph import Agent

app = Agent(node_id="fixer", version="1.0.0", harness_cwd="/srv/repos/checkout")


class Plan(BaseModel):
    summary: str
    files_to_change: List[str]
    risk: str


class Report(BaseModel):
    files_changed: List[str]
    tests_pass: bool
    summary: str


@app.traversal(max_attempts=1, timeout_seconds=3600)
async def fix_failing_test(test: str) -> dict:
    plan = await app.load_checkpoint("plan")
    if plan is None:
        proposed = await app.harness(f"Plan how to make {test} pass without changing the test. Do not edit anything.",
                                     schema=Plan, tools=["Read", "Grep"], timeout=600)
        plan = proposed.parsed.model_dump()
        await app.save_checkpoint("plan", plan, expected_revision=0)

    decision = await app.request_approval({"question": f"Apply this plan for {test}?", "plan": plan},
                                          operation_key=f"fix:{test}", checkpoint=plan)
    if decision["status"] != "approved":
        return {"status": "rejected", "plan": plan}

    applied = await app.harness(f"Apply this plan and run the tests: {plan['summary']}",
                                schema=Report, tools=["Read", "Grep", "Edit", "Bash"], timeout=1800)
    return {"status": "applied", **applied.parsed.model_dump()}

    The checkpoint means the planning run happens once even though the handler replays after the approval; max_attempts=1 means a failed apply is reported, not retried against a half-edited tree. Tool names are passed through to the CLI as given (--tools Read,Grep,Edit for claude-code); codex maps any tools to --sandbox workspace-write, and opencode needs allow_default_tools=True.

    atfHar configuration and Databricks authentication

    atf-harness reads ~/.atf-harness/agent/config.yml for model roles (modelRoles.default: provider/model:variant) and models.yml for endpoints and credential resolvers. An entry such as apiKey: DATABRICKS_TOKEN expects that variable in the worker's process environment; a terminal, a launchd service and a container each have their own environment, and the runtime falls back to the literal string when the variable is absent, which shows up as a misleading 401.

    For a short local check against a Databricks Model Serving endpoint, hand the worker a cached OAuth token from an explicitly selected CLI profile without writing it anywhere:

    DATABRICKS_TOKEN="$(databricks auth token <PROFILE> --output json | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')" \
  python -m atfgraph.worker --module examples.harness.python.agent:app

    That token expires; a long-running worker needs a refresh strategy. ATFGRAPH_HARNESS_MODEL selects the model the example passes and ATFGRAPH_HARNESS_THINKING overrides the variant (--thinking for atf-harness, model_reasoning_effort for codex). Never put a token in agentnode.yaml or a test fixture. The graph server never sees the credential.

    Remote harness: the same call, a workspace on another machine

    Everything above runs a CLI as a child process on the worker, in a local cwd. Remote mode sends the same prompt over HTTPS to an ATF Harness service and runs it in a workspace on that host. ATFGraph stays the control plane: identity, queueing, cancellation, the execution path, approvals and usage are recorded here exactly as for local mode; the harness runs the model loop and tools.

    Toolstools= per callfixed by the operator's harness profile; callers cannot choose tools

    from atfgraph import Agent
from atfgraph.harness import ExistingWorkspace, RemoteHarness

app = Agent("remote-coder")
remote = RemoteHarness(
    base_url=os.environ["ATFGRAPH_HARNESS_URL"],
    profile="coding-safe",                 # operator-approved profile
    edge_auth="databricks",                # or None: what the proxy in front of the harness wants
    app_token_env="ATFGRAPH_HARNESS_TOKEN",  # optional harness application token, named, never passed
)

@app.traversal(max_attempts=1)
async def implement(task: str) -> dict:
    result = await app.harness(task, transport=remote, workspace=ExistingWorkspace("/workspaces/project"), timeout=1200)
    return {"text": result.text, "session": result.remote.session_id, "turn": result.remote.turn_id}

    Exactly one of cwd and workspace is accepted; the wrong combination fails before any I/O. Remote mode is available for provider="atf-harness" only, and tools=, model=, resume= and other local options are rejected because the profile decides them.

    Authentication has two layers that never share a header. Authorization belongs to whatever proxy stands in front of the harness: with edge_auth="databricks" the SDK obtains and refreshes a workspace token through databricks-sdk unified auth (pip install 'atfgraph[databricks]'; a laptop names its profile in ATFGRAPH_DATABRICKS_PROFILE, a Databricks App needs nothing). The harness's own application token, if the operator configured one, is sent as X-Atfhar-Token and is read from the environment variable you name. No token appears in a repr, an error or a progress event.

    Sessions and replay. The first call in an ATFGraph session creates a harness session (idempotently, keyed by the ATFGraph session and workspace) and remembers it in session memory; later calls reuse it. Each turn carries an idempotency key derived from the traverser and the call, so a retried attempt or a continuation after a durable pause re-attaches to the same turn rather than starting another. result.remote tells you what happened: session_id, turn_id, turn_status, session_replayed, turn_replayed, the request_ids that were raised, and stats as the harness reported them.

    Approvals. When the harness asks for confirmation (a tool outside the profile's allow list), the traversal pauses through app.request_approval with the operation key harness:<session>:<request> and a checkpoint holding only session/turn/request references. Decide it as any other approval (atfg, the console, Client.decide_approval); on continuation the bridge answers the harness once and follows the turn to its end. An input/select/editor request cannot be answered from a traversal and is cancelled immediately, so nothing hangs.

    Streams. The bridge follows the harness's SSE stream, reconnects from the last sequence after an overflow, and on reset_required resynchronizes from the session snapshot instead of pretending continuity. If the stream ends early it polls the turn.

    Doctor and protocol. await app.remote_harness_doctor(remote) reports reachability (/healthz), readiness (/readyz), the harness's protocol version and feature flags (/v1/compatibility) and whether the profile is served, without starting a turn; app.harness_doctor() still reports local CLIs. Every remote call first checks that the harness speaks protocol v1; another version, or a harness too old to report one, is refused with protocol_mismatch / protocol_unknown before any session is created.

    What the first slice does not do: clone a repository, return a patch or change artifact, or survive a harness restart mid-turn. The harness has no such contracts yet; when it does, they arrive as new typed options, not as a change to this call.

    Where a harness cannot run

    The worker must be able to spawn the CLI. atf-harness is a Bun application, so a worker running as a Databricks App, which has no Bun and no arbitrary binaries, cannot use it; select another provider there with ATFGRAPH_HARNESS_PROVIDER or give that node its own container image with the CLI installed. The same applies to any hosted worker whose image lacks the binary: harness_doctor reports available: false and the run fails with HarnessFailure("<binary> is not installed in this worker environment") before anything starts. A harness also cannot reach a developer's laptop; cwd is a directory on the worker host.

    Testing a harness capability

    Every harness test in the repository runs against a fake CLI that speaks the provider's JSON-lines dialect, so tests are fast, free and deterministic; binary= points the bridge at it. Adapted from fake_cli in tests/test_authoring_parity.py:

    from __future__ import annotations

import sys
from pathlib import Path

import pytest

from atfgraph import Agent


def fake_cli(tmp_path: Path, name: str, code: str) -> str:
    path = tmp_path / name
    path.write_text(f"#!{sys.executable}\n" + code)
    path.chmod(0o755)
    return str(path)


@pytest.mark.asyncio
async def test_describe_directory_parses_the_schema(tmp_path):
    good = fake_cli(tmp_path, "good-atfHar", """import json
print(json.dumps({"type": "message_end", "message": {"role": "assistant",
      "content": '{"purpose": "demo", "languages": ["python"], "entry_points": ["agent.py"]}',
      "stopReason": "stop"}}))
""")
    app = Agent(node_id="delegate", version="1.0.0", harness_cwd=str(tmp_path))
    result = await app.harness("Describe this directory", binary=good, timeout=30)
    assert "purpose" in result.text

    For an end-to-end test against the real graph server, tests/test_migrated_ops_examples.py puts a fake atfHar on PATH, runs examples/harness/python as a worker, and asserts on the traverser's progress events and output; see 15-testing.md for the daemon fixture it uses.
