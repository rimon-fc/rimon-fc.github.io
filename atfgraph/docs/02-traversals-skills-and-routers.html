Type to search.

    Traversals, skills, typed input and output, routers

    By the end of this page you will know what @app.traversal() and @app.skill() register, how a handler's signature becomes the input and output schema the graph server enforces, when to write a handler as def versus async def, and how to split a large node into AgentRouter groups. It requires only the SDK and a running graph server; every snippet runs with no model provider configured.

    Two capability kinds

    Both decorators register a capability on the node. The difference is the recorded kind, and the convention ../concepts.md attaches to it:

    KindDecoratorConvention
    traversal@app.traversal()Decides a route through the graph; calls other capabilities with await app.traverse(...).
    skill@app.skill()Deterministic, does one thing and returns; does not call through the graph.

    The worker treats the two identically (python/atfgraph/worker.py binds input, runs the handler, completes the task); the SDK does not stop a skill from calling app.traverse. atfg ls prints the kind, and the path shows both as steps. Keep the convention so a path reads as "traversals route, skills do work".

    The registered name is the function name unless you pass one: @app.skill("upper") registers upper. The target you call is always label.capability; app.target("greet") builds it for the node's own label.

    A skill is an API the model can trust

    A skill is any function you write. What it does inside is up to you: call an HTTP API, query a database, invoke an MCP tool, read a file, compute. "Deterministic" here means it does not call a model and does not call other capabilities through the graph, not that it cannot do I/O. examples/python/co_consult's skills are exactly this: hotel_search calls SerpAPI, flight_shop calls Sabre, context_lookup calls an MCP tool.

    The layering is:

    external API or MCP tool  →  @app.skill()  →  a capability on the graph  →  offered to the model as a tool

    The model never sees the API. It sees your skill, with your parameter names, your docstring and your error handling, and every call to it is a recorded step. An API becomes usable by a model only after you have wrapped it in something typed, bounded and observable.

    import httpx

from atfgraph import Agent

app = Agent(node_id="weather", version="1.0.0")


@app.skill()
async def forecast(city: str, days: int = 3) -> dict:
    """Daily forecast for a city from the weather API; days 1-7."""
    async with httpx.AsyncClient(timeout=20) as http:
        response = await http.get("https://api.example.com/forecast", params={"q": city, "days": min(max(days, 1), 7)})
        response.raise_for_status()
        return {"city": city, "days": response.json()["daily"]}


@app.traversal()
async def advise(question: str) -> str:
    # tools="self" offers this node's capabilities; the model sees weather__forecast(city, days)
    return await app.ai(
        system="Answer travel weather questions. Use the forecast tool; never guess.",
        user=question,
        tools="self",
    )
    atfg traverse weather.advise --in '{"question": "Do I need a jacket in Tokyo this weekend?"}'

    The path shows advise with one child step weather.forecast, the API call inside it, and the model's answer built on the result. If the API fails, the skill raises, the model receives an error result and can say so instead of inventing a forecast. Tool loops are covered in 06-model-calls.md.

    Two related things that are different. Consuming MCP tools happens inside a skill, as co_consult does. Publishing is the server's job: with ATFGRAPH_MCP_ENABLED or ATFGRAPH_A2A_ENABLED and app.discovery.publish(...), other agents consume your capabilities the same way (10-multi-node.md). And a skill stays a leaf: if a tool needs to call another node, make it a traversal instead. It still works as a tool.

    Two more kinds: decision and realtime

    @app.decision() registers a capability whose model call reports its own confidence (confidence_field on app.ai), so usage totals can count unsure and fallen-back decisions per capability. @app.realtime(name, provider=, transport=, model=None) registers a realtime entrypoint: it is listed, tagged and publishable over HTTP like any capability, but the graph server refuses POST /api/v2/traversers to it with 400 realtime_entrypoint, because a session is opened by the node (or a browser page through the node) rather than admitted as a traverser; see the hosting guide and examples/python/realtime_browser.

    Tags reach the server

    Tags on a capability (tags=[...]), on a router (AgentRouter(tags=[...])) and on the node (Agent(tags=[...])) are sent with the registration. Rules: at most 16 per capability, each 1 to 64 characters of [a-z0-9_.:-], no duplicates; otherwise registration fails with 400 invalid_tags. Tags drive GET /api/v2/agents?tag=, GET /api/v2/agents/{label}/capabilities?tag=, tag-scoped access policies and POST /api/v2/ard/search {"tags": [...]}.

    Sync and async handlers

    Adapted from examples/python/first_node/agent.py, which has one of each:

    from atfgraph import Agent

app = Agent(node_id="hello", version="1.0.0")


@app.skill()
def shout(text: str) -> dict:
    """Synchronous: runs in a worker thread via asyncio.to_thread."""
    return {"text": text.upper()}


@app.traversal()
async def greet(name: str) -> dict:
    """Asynchronous: runs on the worker's event loop."""
    loud = await app.traverse("hello.shout", text=f"hello {name}")
    return {"greeting": f"Hello {name}", "shouted": loud["text"]}

    An async def handler runs on the worker loop. A plain def handler runs in a thread through asyncio.to_thread; the lease heartbeat runs in its own task, so a blocking handler keeps its lease (tests/python_test_worker.py::test_heartbeats_keep_lease_during_blocking_sync_handler). Two consequences follow from the thread:

    • A sync handler cannot await app.traverse. Use app.traverse_sync(target, **input), which schedules the call on the worker loop and blocks the thread until the child completes (test_traverse_sync_from_thread_handler). Calling traverse_sync from the loop thread raises RuntimeError.
    • Cancellation cannot interrupt a thread. An async handler sees a cancel at its next await; a sync handler runs to its own end and its result is discarded. Prefer async def for anything long.

    current_context() works in both: the worker binds the ExecutionContext with contextvars, and asyncio.to_thread copies the context (python/atfgraph/context.py).

    Typed input

    The input schema is an object whose properties are the handler's keyword parameters (python/atfgraph/schema.py, input_schema_for). Rules the worker applies when it binds the delivered JSON (coerce_input):

    SignatureSchema and binding
    name: str{"type": "string"}, required.
    punctuation: str = "!"Same type, optional.
    brief: dict, tags: list[str]object, array with items.
    `nights: int \None = None`{"type": ["integer", "null"]}.
    body: Brief (Pydantic)Brief.model_json_schema(); the dict is validated with model_validate.
    one Pydantic parameter onlyThe model's fields may also arrive unwrapped at the top level.
    trigger, webhook, execution_contextInjected by the worker; never in the schema; input that sets them is refused.

    A missing required field, an unknown field (unless the handler takes **kwargs) or a Pydantic validation error fails the task with code invalid_input and retryable: false (test_retryable_error_uses_max_attempts_and_progress_is_durable asserts the code). The server also validates input against the registered schema at admission, so a bad request is rejected before a worker sees it.

    Typed output

    The return annotation becomes the output schema (output_schema_for); no annotation, or Any, registers {} meaning any JSON. The worker encodes the returned value with encode_output: Pydantic models through model_dump(mode="json"), dataclasses through asdict, enums to their value. This is the first_node output model:

    from pydantic import BaseModel


class Greeting(BaseModel):
    greeting: str
    shouted: str
    length: int

    tests/python_test_examples.py checks that client.capabilities("hello") reports output_schema["required"] == ["greeting", "shouted", "length"]. The graph server checks the completed output against that schema: tests/test_integration.py::test_registered_schema_rejects_bad_output completes a task with a string where an object was registered and the traverser does not end succeeded. Return the type you declared.

    Capability options

    Every keyword the decorators accept, from AgentRouter.add in python/atfgraph/agent.py:

    OptionDefaultMeaning
    max_attempts1Attempts the server may schedule when the handler raises RetryableError. Shows as retry.max_attempts in definition().
    timeout_seconds300Budget per attempt; the worker stops the handler at it (handler_timeout).
    descriptionfirst docstring lineShown by atfg ls and discovery.
    input_schema, output_schemaderivedOverride the derivation with your own JSON Schema.
    tagsrouter tagsLabels merged with the router's tags.
    triggersnoneEventTrigger / ScheduleTrigger bindings (09-emitters.md).
    accepts_manual_emittersTrueWhether UI-managed emitters may deliver into this capability.

    Adapted from tests/python_test_worker.py::test_decorators_derive_capabilities_and_routers_merge:

    from atfgraph import Agent

app = Agent(node_id="node", version="0.0.1")


@app.traversal(max_attempts=3, timeout_seconds=10)
def plan(brief: dict, nights: int = 3) -> dict:
    return {"ok": True}


caps = app.capabilities()
assert caps["plan"].max_attempts == 3 and caps["plan"].timeout_seconds == 10
assert caps["plan"].input_schema["required"] == ["brief"]

    Routers

    AgentRouter(prefix="", tags=None) groups handlers that an Agent later includes; the decorated functions stay callable. examples/python/co_consult has one router per desk (desks/intake.py, desks/flights.py, ...) and main.py includes them all:

    from atfgraph import Agent, AgentRouter

NODE_ID = "co-consult"
app = Agent(node_id=NODE_ID, version="0.3.0")
router = AgentRouter(tags=["intake"])


@router.traversal()
async def extract_brief(request: str, today: str) -> dict:
    """Given the traveller's sentence, return the structured facts it contains."""
    return {"request": request, "today": today, "confident": True}


@router.traversal()
async def intake_brief(request: str) -> dict:
    extracted = await router.traverse(f"{NODE_ID}.extract_brief", request=request, today="2026-09-15")
    return {"status": "ready", "brief": extracted}


app.include_router(router)

    How the pieces behave, from python/atfgraph/agent.py and tests/python_test_worker.py:

    • prefix is joined to each name with an underscore: AgentRouter(prefix="desk") plus def lookup registers desk_lookup, so the target is node.desk_lookup. co_consult uses no prefix and relies on distinct names.
    • router.traverse, router.submit, router.ai and router.memory forward to the including Agent. Before inclusion, and outside a handler, they raise NoExecutionContext.
    • Including the same name twice raises ValueError (capability ... is registered twice), as does including a router already included in another agent, or an Agent in an Agent.
    • Capabilities added to a router after include_router are adopted too.

    Inspecting what will be registered

    app.capabilities() returns {name: Capability}; app.definition() is the wire body sent by register (label, version, tags, capabilities, each with kind, input_schema, output_schema, retry, timeout_seconds, description, tags and, for realtime, the realtime binding); app.entry(name) returns the CapabilityEntry with the function, tags and triggers. The definition is immutable once registered: a different definition under the same label and version raises ConflictError, and the fix is a new version.

    app.call_local(capability, **input) runs one of the node's own handlers in-process with the same input coercion and output encoding. No traverser is created and nothing is recorded on the graph; it exists for unit tests of handler logic.

    Retained module-level decorators

    from atfgraph import traversal, skill register on the most recently constructed Agent (Agent.get_current()), or on the one passed as agent=. python/atfgraph/decorators.py keeps them for code written against the previous authoring runtime; @app.traversal() is the primary form and the one this guide uses.
