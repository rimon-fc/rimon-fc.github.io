    Monitor workers, traversers and the server over HTTP

    Problem: you want to know what is running, what finished, which workers are connected and whether model endpoints are healthy, from a script or a dashboard rather than the console.

    All requests below were made against a running server. Off loopback, add the ATFGraph key as X-API-Key: <key> (Authorization is reserved for a platform proxy's credential); these operations need the invoke role or higher unless noted.

    The worker fleet: GET /api/v2/workers

    Every enrolled worker with its label, version, capacity, tasks in flight and how long ago it was last seen.

    {"items":[{"capacity":8,"draining":false,"enrolled_at":1789446252988,"expired_leases":0,"id":"e062fdb3-ee04-45fb-9807-4a24a7dcc926","label":"hello","last_seen_age_ms":286,"last_seen_at":1789446274244,"principal":"local","state":"claiming","tasks_in_flight":5,"version":"1.0.0"}],"truncated":false}

    A label that is missing here has no worker: atfg ls will not list it and traversers targeting it stay queued. truncated: true means the list was cut at the server's limit.

    Server-wide counts: GET /api/v2/stats

    {"complete":true,"namespace":"local","oldest_retained_at":1789446272196,"traversers":{"by_status":{"failed":1,"succeeded":4},"in_flight":0,"total":5},"window":{"since":null,"until":null},"workers":{"draining":0,"total":1}}

    traversers.by_status counts every status present; in_flight is the sum of the non-terminal ones. oldest_retained_at tells you how far back the counts reach after retention has pruned older records; complete: false means the window asked for extends past what is retained.

    Model endpoint health: GET /api/v2/model-health

    {"enabled":false,"endpoint_count":0,"endpoints":[],"evaluated_at":1789446030968,"next_check_at":null,"policy":{"check_interval_ms":15000,"check_timeout_ms":5000,"failure_threshold":3,"half_open_max_probes":2,"latency_window":32,"max_concurrent_probes":4,"max_response_bytes":16384,"recovery_timeout_ms":30000,"transition_window":16},"running":false,"status":"disabled"}

    On a server with no model endpoints configured, status is disabled and the policy shows the probe settings that would apply. When endpoints are configured, endpoints lists each with its circuit state and latency window.

    Stored runtime documents: GET /api/v2/runtime/settings

    {"items":[],"limit":256,"namespace":"local","scope":"namespace","total":0}

    Runtime settings are per-namespace documents keyed by name: GET/PUT/DELETE /api/v2/runtime/settings/{key} store and remove one, and POST /api/v2/runtime/settings/{key}/apply applies a stored document to the running process. Saving and applying are separate steps, which is what the console's Settings page also shows. These are administrator operations.

    Listing traversers with paging: GET /api/v2/traversers

    Filters: status, session_id, root_id, principal, roots_only (true/false), limit. Time window: since and until, both milliseconds since the epoch, non-negative integers. Paging: every page returns next_cursor; pass it back as cursor to get the next page, and stop when it is null.

    S=http://127.0.0.1:18880
curl -s "$S/api/v2/traversers?limit=2&roots_only=true"
# {"items":[…two roots…],"next_cursor":"3"}
curl -s "$S/api/v2/traversers?limit=2&roots_only=true&cursor=3"
# {"items":[…the next two…],"next_cursor":null}
curl -s "$S/api/v2/traversers?since=9999999999999"
# {"items":[],"next_cursor":null}

    Malformed paging values are rejected with a 400 envelope rather than ignored:

    {"error":{"code":"invalid_input","message":"cursor is malformed"},"request_id":"…"}
{"error":{"code":"invalid_input","message":"since must be a non-negative integer"},"request_id":"…"}
{"error":{"code":"invalid_query","message":"roots_only must be true or false"},"request_id":"…"}

    Treat cursor as opaque: it is whatever the previous page's next_cursor was. The operation's parameter table in the generated Traversers reference declares all of these.
