    Studio: build an agent node from a brief

    Studio is a product node, studio, that turns a written brief into an ATFGraph agent node through a remote ATF Harness running the ATFGraph builder skills. One build is one ATFGraph session: the plan, every harness event, each approval, the reviewed tree's digest and the deployment are on one path. The Console page for it (Build → Studio) is in progress; everything below already works from atfg and the Python client.

    What a build is

    brief ──► studio.build ──► plan (Opus 5.5 or Fable 5.1 through the harness)
                              │  approval  studio:plan:<label>            ← you decide, optionally answering the plan's questions
                              ▼
                           build turn: scaffold, verify against an isolated daemon, write studio/verification.json
                              │  approvals harness:<session>:<request>    ← each shell command the builder wants to run
                              ▼
                           review: file list, per-file diffs and tree digest from the harness workspace
                              │  approval  studio:accept:<label>:<digest> ← accept the tree, by digest
                              ▼
          studio.deploy ──► plan (read-only) ──► approval studio:deploy:<label>:<digest> ──► the node App is deployed

    The harness workspace is ephemeral. The accepted tree's digest is recorded; studio.deploy fetches the tree again, recomputes the digest and refuses if it differs from what was reviewed. What runs is what you read.

    Running the studio node

    The node needs a harness and a Databricks profile, all from the environment; nothing travels on the wire.

    variablemeaning
    ATFGRAPH_HARNESS_URLthe ATF Harness service, e.g. the atf-harness-pilot App URL
    ATFGRAPH_HARNESS_PROFILEharness profile, default atfgraph-builder
    ATFGRAPH_HARNESS_WORKSPACEone existing directory under the harness's workspace root, shared by every build
    ATFGRAPH_HARNESS_WORKSPACE_ROOTinstead: a root under which each build gets its own studio/<label> directory, created on the harness
    ATFGRAPH_HARNESS_EDGE_AUTHdatabricks behind the Apps proxy (with ATFGRAPH_DATABRICKS_PROFILE on a laptop), else none
    ATFGRAPH_HARNESS_TOKENoptional harness application token, sent as X-Atfhar-Token
    ATFGRAPH_HARNESS_MODELdefault model when the brief names none, e.g. databricks-claude-opus-5-5/databricks-claude-opus-5-5:high
    ATFGRAPH_STUDIO_TURN_TIMEOUTseconds per harness turn, default 1800
    ATFGRAPH_DEPLOY_PROFILEDatabricks CLI profile studio.deploy deploys under on a laptop (bundle engine); never chosen for you
    ATFGRAPH_DEPLOY_API_KEYgraph-server identity that mints node tokens for deployed nodes (an admin identity bound from the studio node's scope, e.g. --bind-secret ATFGRAPH_DEPLOY_API_KEY=deploy-api-key); default: the node's own key
    ATFGRAPH_STUDIO_WHEELthe atfgraph wheel the deployed node bundles; optional when atfg is installed beside its wheel (<prefix>/share/atfgraph)
    python -m atfgraph.worker --module atfgraph.studio.node:app
atfg ls studio          # build, continue, deploy, discard, doctor, schemas
atfg traverse studio.doctor --in '{}'

    studio.doctor reports whether the harness is reachable and ready, its protocol version, and whether the profile is served, without starting a turn.

    A build from the CLI

    atfg traverse studio.build --new-session --in '{"brief": {
  "brief": "A node with one skill reverse(text) that returns the reversed string and its length, and a traversal run(text) that validates the input and calls it.",
  "label": "reverser",
  "model": "databricks-claude-opus-5-5/databricks-claude-opus-5-5:high"
}}'

    The traverser pauses at each approval. Decide them from the Console's Runs page or from a program:

    async with Client(server) as client:
    for approval in await client.list_approvals():
        if approval["operation_key"] == "studio:plan:reverser":
            await client.decide_approval(approval["id"], "approved", {"answers": {"q1": "yes"}})

    Answers to the plan's questions travel in the approval's response; unanswered questions take the plan's defaults. Shell commands the builder wants to run arrive as harness:<session>:<request> approvals with references only; the command text never reaches the path. The final result carries plan, verification, review (files and diff), reviewed_digest, the harness session id and the usage of both turns.

    Deploy, continue, discard

    atfg traverse studio.deploy  --session <build session> --in '{"label": "reverser"}'
atfg traverse studio.continue --session <build session> --in '{"message": "Rename run to reverse_text"}'
atfg traverse studio.discard  --session <build session> --in '{}'

    deploy shows the deploy engine's read-only plan in the studio:deploy:<label>:<digest> approval and runs the real deploy on approval, with the studio node's own Databricks identity. Inside the studio node's App there is no CLI profile: the engine's Apps API path deploys as the App's own service principal (--engine api), uploads the bundle under that principal's workspace home and bundles the wheel the studio App itself runs. continue adds a turn to the same harness session (a new turn once the previous one completed) and, because the turn may change the tree, ends with a fresh review and a new studio:accept:<label>:<digest> approval; deploy then ships that digest. discard deletes the harness session and its pairing; the run records stay.

    The brief

    StudioBrief (atfgraph.studio.schemas, JSON Schema from studio.schemas): brief, label, optional model, attachments (references to files staged under brief/: OpenAPI specs, documents, screenshots, sample payloads), mcp_servers (name, transport, URL or command, the environment variable names its auth needs, tool names) and secrets (variable names with a status: present, provide now, create empty). Credential values never appear in a brief; the builder writes .env.example and the deploy engine fills the node's secret scope from names.

    What gets recorded

    wherewhat
    path of the build runplan turn, build turn, every harness event as a progress event, three approvals
    reviewthe file list, a bounded unified diff per file (entries[].diff, against the empty tree a build starts from) and the tree digest
    checkpointsstudio:plan, studio:built, studio:review (per run)
    session memorythe harness pairing and the accepted build (studio.review: label, digest, files)
    run metadatastudio.label, studio.stage (planning, review, accepted, deploying, deployed, …)
    usageboth turns' tokens (cache reads and writes count as input, reported separately too) and provider-reported cost; the harness's 0 for an unpriced route is recorded as unknown so the server's price table applies

    Governing who may deploy

    Building and deploying are separate capabilities, so a policy can allow one and deny the other. An access policy that lets a principal build but not deploy:

    {"name": "studio-no-deploy", "label": "studio", "capability": "deploy", "principal": "builders", "effect": "deny"}

    installed through POST /api/v2/access/policies as in the access-boundaries example. The deploy itself runs under the studio node's service principal, which needs Apps create/deploy, secret scope create/put and admin on the graph server namespace in the target workspace; grant those to the node App before the first studio.deploy.

    Limits and known gaps

    • Remote mode fixes tools and model by harness profile; a per-call dollar cap is not available remotely. The profile's turn limits and the node's budget policy bound a build.
    • Durability (what survives what). Harness sessions are stored on disk and survive a harness restart, an App redeploy and an idle stop; a turn that was running when the harness stopped ends as turn_aborted and continue starts the next turn in the same session; the harness event journal is in memory, so a client resuming with a cursor gets reset_required and replays; workspace files are lost on an App redeploy or idle stop. Because the accepted tree is identified by its digest and fetched again at deploy time, a workspace lost between accept and deploy makes studio.deploy refuse ("changed since review") instead of shipping something else: run continue to rebuild and re-accept. Databricks Apps stop an idle harness App; a stopped harness shows in studio.doctor as unreachable until it is started again.
    • The verification table is the builder's own report and can be honest about what it could not run: on a harness without the ATFGraph runtime the daemon-backed checks come back skipped and the build is accepted_with_failures. The deployed node still runs (live proof 2026-09-27: a brief became App atfgraph-node-reverser-b4 and answered run(text) on the graph server), but a skipped check is not a passed one; read the table before you deploy.
